## 1. 文档说明

本文档既是**测试计划**（测什么、怎么测、通过标准），也是**测试报告**（实际跑出什么、发现什么、修了什么）。

按"照之能重现"的要求，本文做到三点：

1. 每个用例都给出**可执行的输入**与**可观察的输出**（HTTP 状态码、数据库字段值、界面元素）；
2. 每个用例都注明**执行命令**，读者在本机照抄即可复现同一结果；
3. 发现缺陷时记录**复现步骤 + 根因 + 修复点 + 回归用例编号**，形成闭环。

## 3. 测试策略

### 3.1 分层策略

| 层次 | 目标 | 手段 | 用例数 | 是否需要数据库 |
|---|---|---|---|---|
| L1 单元/接口测试 | 路由门禁、鉴权、票据状态机、计费闸门等"规则型"逻辑 | PyUnit + Flask `test_client` | 32 | 部分需要 |
| L2 端到端核验 | 一条完整业务链路（存件 → 取件 → 超时 → 缴费）跨接口、跨表的一致性 | 独立脚本 `logs/e2e_check.py` | 15 项检查 | 需要 |
| L3 界面核验 | 三端页面渲染、元素可见性、文案与状态映射 | 手工用例 + Chrome headless 截图比对 | 8 条手工用例 / 6 张截图 | 需要 |

分层理由：本项目绝大多数缺陷集中在"**页面层挡住了、接口层没挡**"这类边界上（D-01、D-02 均属此类），因此 L1 重点打接口，而不是打函数；L2 专门验证**跨表副作用**（取件后格口是否释放、流水是否生成），这是单元测试看不到的。

### 3.2 通过准则

| 级别 | 准则 |
|---|---|
| 阻塞 | P0/P1 缺陷为 0，且 L1 通过率 100% |
| 可发布 | L1 通过率 100%，L2 通过率 100%，L3 无阻断性视觉缺陷 |
| 可演示 | 上述全部满足，且演示数据齐备（3 件待取包裹，含 1 件超时待缴） |

### 3.3 用例编号规则

`TC-<模块>-<序号>`，模块取值为：

| 前缀 | 模块 | 对应用例 |
|---|---|---|
| `A` | 认证与权限 | 后台登录、会话 Cookie、触屏 token、匿名越权 |
| `R` | 路由与缓存 | 页面门禁、静态白名单、HTML no-store |
| `E` | 实体 CRUD | 写操作鉴权、读操作开放、级联引用预检 |
| `Q` | 扫码登录票据 | 建票、确认、轮询、过期、重放 |
| `K` | 核心业务 | 存件、取件码取件、超时计费、格口释放 |
| `M` | 手机端 | 票据确认页、取件预览与开柜 |

缺陷编号 `D-<序号>`，与用例编号交叉引用。

## 4. 测试计划

### 4.1 范围与优先级

| 优先级 | 范围 | 理由 |
|---|---|---|
| P0 | 存件分配格口、取件码取件、超时计费阻断、格口释放 | 主流程，错一处系统不可用 |
| P0 | 后台会话鉴权、接口写操作鉴权 | 错则数据可被任意篡改 |
| P1 | 扫码登录票据全链路（建票→确认→轮询→消费） | 柜机主入口，涉及一次性凭据安全 |
| P1 | 通知入队与幂等（不阻塞主流程） | 错则存件变慢或重复打扰 |
| P2 | 统计报表、异常登记、寄件/揽件 | 旁路功能 |
| P3 | 界面文案、图标、响应式布局 | 不影响功能 |

### 4.2 执行顺序

1. 建库建表 → 导入基线数据（`init_database.sql`）；
2. 跑 L1 单元测试（无副作用，可反复执行）；
3. 跑 L2 端到端核验（**有副作用**，脚本自带清理，跑完库回到基线）；
4. 起服务做 L3 界面截图核验；
5. 复原演示数据（`scripts/reset_demo_data.py`）。

## 5. L1：单元与接口测试（PyUnit）

### 5.1 运行方式

**前置条件（v1.1 补充，缺一不可）**：数据库必须先执行 `db/objects.sql` 建好视图与触发器。

```bash
# 0) 前置检查：期望 2 / 1 / 3
mysql -uroot -p smart_locker -e "
  SELECT (SELECT COUNT(*) FROM information_schema.VIEWS
           WHERE TABLE_SCHEMA='smart_locker')    AS views_,
         (SELECT COUNT(*) FROM information_schema.TRIGGERS
           WHERE TRIGGER_SCHEMA='smart_locker')  AS triggers_,
         (SELECT COUNT(*) FROM information_schema.ROUTINES
           WHERE ROUTINE_SCHEMA='smart_locker')  AS procs_;"
# 不等于 2/1/3 则先执行：
mysql -uroot -p smart_locker < db/objects.sql

# 1) 跑测试
cd backend
python -m unittest discover -s tests -p "test_*.py" -v
```

> **注意 `-p "test_*.py"` 与 `-t`**：在仓库根目录用 `-s backend/tests -t .` 会因 `backend/tests`
> 不是可导入包而报 `ImportError: Start directory is not importable`。正确做法是 `cd backend`
> 后执行上面这条，或用 `-s backend/tests` 不加 `-t`。

`test_qr_login.py` 与 `test_pickup_payment_gate.py` 均以 `unittest.skipUnless(_db_ready(), ...)` 保护：**数据库连不上时整类跳过而不是报错**，保证无库环境也能跑通（结果为 skip 而非 fail）。`test_route_separation.py` 只打页面路由与鉴权，不碰数据表，无需 MySQL 即可执行。

**两个已知的环境陷阱（不是代码 bug）**：

| 症状 | 原因 | 处理 |
|---|---|---|
| `test_pickup_succeeds_after_payment` 报 `AssertionError: 'OCCUPIED' != 'FREE'` | 缺触发器 `trg_package_after_update`，取件后格口不释放 | 执行 `db/objects.sql` |
| `test_entity_mutation_allowed_with_admin` 报 `AssertionError: 400 != 201` | 上次运行被强杀，残留 `ZZTEST` 公司行触发唯一键冲突 | `DELETE FROM t_express_company WHERE company_code='ZZTEST';` |

> 第二条尤其值得记：测试本应在 `delete` 中自清理，但进程被强杀时清理不会执行。
> 这也说明**测试自带清理不等于测试幂等**，环境恢复仍需人工兜底。

## 6. L2：端到端核验

### 6.1 脚本与运行方式

脚本：`logs/e2e_check.py`（一次性核验脚本，不入版本库）

```bash
python logs/e2e_check.py
```

脚本设计要点：

- 走 Flask `test_client`，**不启动 HTTP 服务、不占端口**，可在 CI 里跑；
- 设 `NOTIFY_WORKER=0`，避免后台线程干扰；
- 使用专用手机号 `13700001234` 建测试用户，`purge_leftovers()` 在开头按该手机号清理上次中断的残留，`cleanup()` 在 `finally` 中还原；
- 清理顺序严格遵循外键：`t_notice` → `t_exception_log` → `t_pickup_record` → `t_device_command` → `t_package` → `t_user`，最后把格口置回 `FREE`。

### 6.3 一个必须记录的准备细节

构造"已超时"样本时，直接把 `expire_time` 改到过去会触发 `chk_pkg_time`（`expire_time > store_time`）约束报错。正确写法是**同时把 `store_time` 前移**，保持两者相对关系：

```sql
UPDATE t_package SET status='EXPIRED', overtime_fee=1.00, overtime_fee_paid=0,
       store_time  = DATE_SUB(NOW(), INTERVAL 73 HOUR),
       expire_time = DATE_SUB(NOW(), INTERVAL 1 HOUR)
WHERE package_id = %s;
```

73 = 48（免费期）+ 24（超时 1 天）+ 1（余量）。这条约束在测试中反向证明了数据库层的业务规则是生效的——**约束不是文档里的装饰，它会真的拦住错误的测试数据**。

## 8. 缺陷记录

测试期间共发现并关闭 5 项，其中 2 项为**安全/资损级**。

### D-01 取件码取件绕过超时保管费（严重：高）

| 项 | 内容 |
|---|---|
| 发现阶段 | L2 端到端核验，TC-K-03a 首跑失败（返回 200 而非 402） |
| 复现步骤 | 1) 存一件包裹；2) 改库置 `status='EXPIRED'`、`overtime_fee=1.00`、`overtime_fee_paid=0`；3) `POST /api/business/pickup {pickup_code:<码>}` |
| 实际 | 200，包裹直接置 `PICKED`，未收一分钱 |
| 预期 | 402 `NEED_PAYMENT`，状态保持 `EXPIRED` |
| 根因 | `/api/business/pickup` 只判 `PICKED` / `RETURNED` / `EXCEPTION` 三态，漏了"`EXPIRED` 且未缴费"。同一文件的 `_do_unlock`（开柜接口）有这道判断，两条取件路径的规则不一致。更麻烦的是**顺序**：一旦置 `PICKED`，包裹就脱离 `EXPIRED`，`pay-overtime` 的过滤条件 `status='EXPIRED'` 再也匹配不到它，这笔账永久收不回（TC-K-03b 首跑 `paid_count=0` 正是这个后果） |
| 修复 | `business.py` 的 `pickup()` 在置 `PICKED` **之前**加闸门，返回 402 并带 `package_id` 与 `overtime_fee`；`kiosk.js` 的 `doCodePickup()` 捕获 402 → 弹支付层 → 支付成功后用同一取件码自动重试 |
| 回归 | `test_pickup_payment_gate.py` 3 条（TC-K-03a/b/c）；L2 的 TC-K-03a/b/c 复跑通过 |

### D-02 实体写接口无任何鉴权（严重：高）

| 项 | 内容 |
|---|---|
| 发现阶段 | 设计复查（写测试用例时追问"如果直接打接口会怎样"） |
| 复现步骤 | 未登录状态下 `curl -X DELETE http://127.0.0.1:5000/api/packages/1` |
| 实际 | 直接删库成功 |
| 预期 | 401 |
| 根因 | 页面层用 `before_request` 挡住了 `/admin/*`，但 `/api/*` 接口层没有任何校验。门禁装在**门**上，没装在**墙**上 |
| 修复 | `entities.py` 加 `_guard_mutations`：对 `POST/PUT/DELETE/PATCH` 校验后台会话，未登录返回 401；`GET` 保持开放（触屏端投递记录、手机端选柜体依赖 GET） |
| 回归 | `test_route_separation.py` 新增 3 条：`test_entity_mutation_requires_admin`、`test_entity_read_stays_open`、`test_entity_mutation_allowed_with_admin` |

### D-03 `[hidden]` 属性失效，登录条常显（一般：中）

| 项 | 内容 |
|---|---|
| 发现阶段 | L3 界面核验，未登录首页仍显示"退出登录"按钮 |
| 根因 | 浏览器默认 `[hidden] { display: none }` 的优先级低于类选择器 `.login-bar { display: flex }`，元素带 `hidden` 属性却照样渲染 |
| 修复 | `kiosk.css` 与 `mobile.css` 顶部各加一条 `[hidden] { display: none !important; }` |
| 回归 | 截图 `kiosk-home.png` / `kiosk-auth.png` 对比确认 |

### D-04 触屏端可"返回首页"退回旧门户页（一般：中）

| 项 | 内容 |
|---|---|
| 发现阶段 | 用户试用反馈 |
| 根因 | 两处叠加：① 旧的 `/index.html` 门户页仍在磁盘上，历史链接可达；② HTML 响应未禁缓存，浏览器回退时直接读缓存里的旧页面 |
| 修复 | 删除门户页，`/` 与 `/kiosk` 统一指向 `kiosk.html`，旧 URL 302 重定向；`after_request` 对 HTML 加 `Cache-Control: no-store` |
| 回归 | `test_route_separation.py` 的 `test_root_serves_kiosk`、`test_kiosk_alias`、`test_legacy_urls_redirect`、`test_html_is_not_cached` |

### D-05 手机端"扫码取件"与柜机票据功能重复（设计冗余：低）

| 项 | 内容 |
|---|---|
| 发现阶段 | 需求评审 |
| 现象 | 二维码语义已从"取件码"改为"登录柜机票据"后，手机端应用内的"扫一扫取件"成了重复入口，且受 `getUserMedia` 的 HTTPS 限制，实际不可用 |
| 处理 | 删除手机端 `#scanCard`、快递员页扫码卡片、`#scanner` 浮层及 `startScan` / `stopScan` / `handleScanText` 三个函数与相关 CSS；保留系统相机扫码进票据页的主路径 |
| 验证 | 手机端票据页 / 用户首页 / 快递员首页截图无残留入口；`node --check` 通过 |
