# 静音演示视频 · 分镜清单与复现说明

> **产物**：`deliverables/智能快递柜系统_静音演示视频.mp4`
> **规格**：1920×1080 · H.264 (High, level 4.1) · 30 fps · **无音轨** · 8 分 11 秒 · 约 5.9 MB
> **性质**：全部画面由 `quality/video/record_demo.js` 以 CDP 驱动真实 Edge，
> 对**真实运行的系统**执行真实操作后逐帧抓取 —— **不是静态幻灯片拼接**。
> 每个场景的操作都打到了真实后端接口，页面内容由服务端返回的数据渲染。

## 一、为什么是"抓帧"而不是"录屏软件"

| 常规方案 | 本机实测结果 |
|---|---|
| OBS Studio | ❌ 未安装（`obs64` 不在 PATH，常见安装路径也均不存在） |
| ffmpeg 命令行 | ❌ 未安装（`ffmpeg`/`ffprobe` 均不在 PATH） |
| Edge / Chrome CDP | ✅ 两者都在，Node 22 自带 WebSocket |

因此采用：**headless 浏览器 + CDP `Page.captureScreenshot` 固定间隔抓帧 → ffmpeg 合成**。
ffmpeg 二进制来自 `pip install imageio-ffmpeg`（自带 gyan.dev essentials build，
含 libx264），不是系统级安装，不污染环境。

抓帧路径的关键优势：截的是**浏览器渲染结果**，鼠标移动、输入字符、视图切换
都会真实反映在画面上，与录屏软件得到的画面等价。

## 三、复现步骤（从零到成片）

```powershell
# 0) 前置：服务必须在跑（另开终端）
python backend\app.py
#   健康检查：Invoke-WebRequest http://127.0.0.1:5000/api/health
#   期望 {"db":"connected","status":"ok"}

# 1) 造演示数据：在 CAB-001 上现造 1 件待取 + 1 件超时未缴（走真实存件接口）
python quality\tools\prepare_demo_packages.py
#   产出取件码写入 quality/logs/video-shots/demo_codes.json

# 2) 录制：CDP 驱动真实浏览器，按 11 个场景执行真实操作并抓帧
node quality\video\record_demo.js --out quality\logs\video-shots --fps 4 --pace 2 --hold 4500
#   --fps 4      抓帧频率（4 帧/秒足够，合成时插到 30fps）
#   --pace 2     所有操作与停留放慢 2 倍，给静音片留出读字幕的时间
#   --hold 4500  每个场景结束后额外停留 4.5 s
#   产出：<out>/<场景>/frames/*.png、concat.txt、manifest.json

# 3) 合成：章节卡 + 真实画面 + 片头片尾 → 1920x1080 H.264 无音轨
python quality\tools\build_demo_video.py
#   产出 deliverables\智能快递柜系统_静音演示视频.mp4
```

### 只重录某几个场景

`prepare_demo_packages.py` 每跑一次都会消耗一件待取件（会被取走），所以
**重录前先重跑它**，否则取件场景会录到"该包裹已取走"：

```powershell
python quality\tools\prepare_demo_packages.py
node quality\video\record_demo.js --only 04_kiosk_pickup,05_kiosk_expired --pace 2 --hold 4500
python quality\tools\build_demo_video.py
```

## 五、录制过程中真实踩到的坑（都已在脚本里修掉）

这些不是"写完就过"的流程，是实际调试记录，写下来供复现时少走弯路：

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | 某场景只抓到 9 帧就停滞，后续帧全部重复 | 支付弹窗带 `backdrop-filter` 模糊背景时，`Page.captureScreenshot` 偶发长时间不返回，`busy` 标志永久卡死 | 给抓帧加 2.5 s 超时保护（`Promise.race`），超时跳过该帧而不是挂死 |
| 2 | 手机端所有场景都停在登录页，57 帧完全相同 | `send-code` 有 60 s 限流，连录多个手机场景时第二次返回 429，登录静默失败 | 识别 429 → 等冷却重试一次；仍失败则**抛错**，不伪造画面 |
| 3 | 取件场景录到"取件失败·该包裹已取走" | 讲稿写死的 549548 在之前联调中已被取走 | 开录前查真实可用码，改为动态取件 |
| 4 | 取件场景录到"该取件码不属于当前柜体" | 库里的 STORED 件在 CAB-002/CAB-030，柜机首页在 CAB-001，接口有柜体归属校验 | `prepare_demo_packages.py` 在 CAB-001 上现造数据；脚本比对柜体并告警 |
| 5 | 全量拉 `?page=1&size=200` 查不到目标包裹 | 库里 310 条，STORED 只有 2 条且在末页 | 改为按 `status` 过滤分别查 |

另有一个**本任务之外但值得记录**的缺陷：`scripts/reset_demo_data.py` 在 GBK 控制台下
打印 `¥` 会抛 `UnicodeEncodeError`。绕过方式是设 `PYTHONIOENCODING=utf-8`；
脚本本身未改（不属于 quality 所有权范围），已在本文件记录。
