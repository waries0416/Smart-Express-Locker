## 2. 数据库设计

### 2.1 实体关系

```
                    t_express_company
                      │ 1
                      ├──────────────< t_courier >──────────┐
                      │                   1                  │
                      │                   │                  │
                      │                   └──────┐           │
   t_user >───────────┼── t_package ────────────┘           │
     1                │      │ 1                             │
     │                │      ├────────< t_pickup_record      │
     │                │      ├────────< t_exception_log      │
     │                │      ├────────< t_notice             │
     │                │      └──< t_package (from_send_id 自引用)
     │                │
     └───────────────>┤      t_cabinet >──< t_cell
                           1      │           1
                                  ├──────< t_device_command
                                  └──────< t_qr_ticket
```

| 关系 | 基数 | 说明 |
|---|---|---|
| 快递公司 → 快递员 | 1 : N | 一个公司有多名快递员 |
| 快递员 → 包裹 | 1 : N | 一名快递员经手多个包裹（`ON DELETE RESTRICT`，历史留档） |
| 用户 → 包裹 | 1 : N | 一个用户名下有多个包裹（收件与寄件都在 `t_package`） |
| 柜体 → 格口 | 1 : N | 一个柜体含多个格口（`ON DELETE CASCADE`） |
| 格口 → 包裹 | 1 : N | 一个格口历史上承载多个包裹，同一时刻最多一个在柜 |
| 包裹 → 取件流水 | 1 : N | 每次开柜尝试一条记录（成功与失败都记） |
| 包裹 → 异常日志 | 1 : N | 一个包裹可多次异常 |
| 包裹 → 通知 | 1 : N | 一个包裹可产生多条通知（存入、提醒、超时、取件回执） |
| 包裹 → 包裹（`from_send_id`） | 1 : 1 | 快递员存件时关联的寄件单，实现"寄件—投递"闭环 |
| 柜体 → 指令 | 1 : N | 手机端远程开柜指令队列 |
| 柜体 → 票据 | 1 : N | 扫码登录票据 |

### 2.3 表结构

#### 2.3.1 t_express_company（快递公司）

| 列名 | 类型 | 约束 | 说明 |

### 2.4 视图 v_package_detail

把包裹与柜体、格口、快递员、公司、用户、寄件单关联成一张宽表，避免各业务函数重复写 6 表 JOIN：

```
t_package p
  JOIN t_cabinet cab       ON cab.cabinet_id = p.cabinet_id
  JOIN t_cell cell         ON cell.cell_id   = p.cell_id
  LEFT JOIN t_courier cr   ON cr.courier_id  = p.courier_id
  LEFT JOIN t_express_company c ON c.company_id = cr.company_id
  JOIN t_user u            ON u.user_id      = p.user_id
  LEFT JOIN t_package send ON send.package_id = p.from_send_id
```

列包含 `package_id, user_id, direction, tracking_no, pkg_status, size_type, weight, pickup_code, store_time, expire_time, pickup_time, note, recipient_name, recipient_phone, from_send_id, overtime_fee, overtime_fee_paid, cabinet_code, location, cell_code, courier_name, company_name, user_name, user_phone, send_code, send_tracking_no`。

> 注意 `status` 在视图中别名为 `pkg_status`，避免与柜体/格口状态混淆。

### 2.5 约束设计说明

| 约束类型 | 数量 | 典型例子 | 设计意图 |
|---|---|---|---|
| 主键 | 12 | `package_id` | 代理主键，业务键另设唯一约束 |
| 唯一键 | 9 | `tracking_no`、`pickup_code`、`(biz_key, channel, role, id)` | 业务唯一性由数据库兜底，不依赖应用层查重 |
| 外键 | 15 | `t_package.cell_id → t_cell` | 引用完整性；历史数据用 RESTRICT，设备数据用 CASCADE |
| CHECK | 36 | `chk_pkg_status`、`chk_qr_confirm`、`chk_pkg_time` | 枚举与业务不变式在数据库层强制 |
| 正则 CHECK | 5 | `chk_user_phone` = `^1[3-9][0-9]{9}$` | 手机号格式数据库级校验（MySQL 8 `REGEXP_LIKE`） |

**为什么把枚举写成 CHECK 而不是字典表**：枚举值稳定且数量少（如 8 种包裹状态），建字典表会引入 4 次额外 JOIN 却带不来收益；CHECK 能在写入时立刻拒绝非法值，比应用层校验更可靠。

### 2.6 范式与冗余说明

- 12 张表均满足 3NF：非主属性完全依赖主键，无传递依赖；
- **有意的冗余**：`t_cabinet.total_cells` 是统计列，可从 `t_cell` 聚合得到。保留它是为了柜体列表页不必对 720 行做 `GROUP BY`；一致性由 `entities._sync_cabinet_cells()` 与 `_recalc_cabinet_total()` 在事务内维护；
- **有意的反范式**：`t_notice.recipient_name/recipient_phone` 冗余存储接收者信息。通知是历史事实，接收人后续改手机号不应影响已发通知的内容。

## 3. 接口清单

统一前缀说明：`/api/*` 通用资源，`/api/business/*` 业务流，`/api/m/*` 手机端，`/api/qr/*` 扫码，`/api/device/*` 柜机设备。

鉴权列含义：`—` 无需鉴权；`Admin` 需管理员 Cookie；`Bearer` 需 `Authorization: Bearer <token>`；`Bearer(USER)` 表示还需角色为 USER。

### 3.1 页面路由

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 触屏端首页（默认入口） |
| GET | `/kiosk` | 触屏端别名，支持 `?cabinet=N` 绑定柜体 |
| GET | `/m`、`/m/` | 手机端 H5 |
| GET | `/m/<path>` | 手机端静态资源 |

### 3.3 通用实体 `/api/*`

`<entity>` ∈ `companies | couriers | users | cabinets | cells | packages`。

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/<entity>` | — | 列表；支持 `page/size/search` 与实体专属过滤（如 packages 的 `status`、`recipient_phone`、`store_time_from/to`） |
| GET | `/<entity>/<id>` | — | 单条详情 |
| POST | `/<entity>` | Admin | 新增；柜体会同步生成格口 |
| PUT | `/<entity>/<id>` | Admin | 修改 |
| DELETE | `/<entity>/<id>?force=1` | Admin | 删除；有关联时先返回 409 + 引用明细，`force=1` 走事务级联 |
| GET | `/<entity>/<id>/refs` | — | 删除前引用预检 |

### 4.4 超时计费

```

③ 缴费：POST /api/m/pay/overtime {package_ids:[...]}
         → 校验全部属于本人（否则 403）
         → charge_overtime() 置 overtime_fee_paid=1
④ 开柜：缴费后 do_unlock() 不再返回 NEED_PAYMENT，正常开柜
```

## 5. 状态机

### 5.1 包裹状态

```
                    ┌──────────── 存件 ────────────┐
                    ▼                              │
   (新建) ────> STORED ──── 取件 ────> PICKED       │
                  │                                │
                  │ 到期未取                        │ 寄件下单
                  ▼                                ▼
               EXPIRED ──── 取件 ────> PICKED   SEND_WAIT_PICKUP
                  │                                │ 揽收
                  ├── 退回 ───> RETURNED           ▼
                  └── 异常 ───> EXCEPTION      SEND_COLLECTED
                                                   │ 撤回
                                                   ▼
                                              SEND_CANCELLED
```

| 状态 | 含义 | 是否占格口 | 可执行动作 |
|---|---|---|---|
| STORED | 已存入，未超时 | 是 | 取件、退回、标记异常 |
| EXPIRED | 已超时未取 | 是 | 缴费后取件、退回 |
| PICKED | 已取走 | 否 | 重新开门（5 分钟内） |
| RETURNED | 已退回 | 否 | — |
| EXCEPTION | 异常 | 是 | 管理员处理 |
| SEND_WAIT_PICKUP | 寄件待揽收 | 是 | 揽收、撤回 |
| SEND_COLLECTED | 寄件已揽收 | 否 | 作为存件关联源 |
| SEND_CANCELLED | 寄件已撤回 | 否 | — |

### 5.2 票据状态

```
   PENDING ──手机确认──> CONFIRMED ──柜机轮询──> CONSUMED (终态)
      │                     │
      ├── 超时 ──> EXPIRED   └── （CONFIRMED 后不再判超时，允许柜机补消费）
      └── 柜机刷新/取消 ──> CANCELLED
```

### 5.3 指令状态

```
   PENDING ──柜机轮询取走──> SENT ──回执成功──> ACK (终态)
                                └──回执失败──> FAILED (终态)
```

## 6. 关键实现要点

### 6.1 票据原子消费（防重放）

```python
n = db.execute("UPDATE t_qr_ticket SET status='CONSUMED', consumed_at=NOW() "
               "WHERE ticket_id=%s AND status='CONFIRMED'", (tid,))
if n != 1:                      # 另一个轮询已经消费掉了
    return jsonify({"status": "CONSUMED", "token": None})
return jsonify({"status": "CONSUMED", "token": issue_kiosk_token(role, rid)})
```

依赖 `UPDATE ... WHERE status='CONFIRMED'` 的 `rowcount` 做 CAS，而不是"先查后改"——后者在并发下会双发 token。

### 6.2 幂等键（防重复开柜）

```python
if idem_key:
    dup = db.query_one("SELECT response_json FROM t_device_command WHERE idempotency_key=%s", (idem_key,))
    if dup and dup["response_json"]:
        return jsonify(json.loads(dup["response_json"]))   # 直接复用首次结果
```

并发下若插入撞唯一键，异常分支同样回查快照返回。

### 6.3 费用口径同源

`_fee_of(r, need_pay)` 被预览、开柜、缴费三处共用：有 `overtime_fee` 用它，没有则按 ¥1.00。避免出现"预览 0 元、实扣 1 元"的体验断层。

### 6.4 身份结构统一

`auth.build_identity(role, rid)` 被 `kiosk-verify`、票据确认、票据轮询三处共用，保证前端只需一套渲染逻辑。

### 6.5 显式事务

`db.transaction()` 用 `SET AUTOCOMMIT=0/1` 而非 `conn.autocommit(False)`，因为连接池返回的是 SteadyDB 包装连接，不暴露 PyMySQL 的该方法。

### 6.6 通知惰性重试

worker 每 15 秒取 `status='PENDING' AND (next_retry_at IS NULL OR next_retry_at<=NOW())` 的批次；失败按 `[30,120,600]` 退避设置 `next_retry_at`；`retry_count >= 3` 置 FAILED。

### 6.7 页面不缓存

`after_request` 对 HTML 加 `no-store, no-cache, must-revalidate, max-age=0`，静态资源 `no-cache`（保留 ETag/304）。目的是杜绝"浏览器拿缓存里的旧页面继续返回已删除的门户页"。

| # | 限制 | 影响 | 改进方向 |
|---|---|---|---|
