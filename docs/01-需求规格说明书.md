## 1. 文档说明

### 1.1 编写目的

本文档定义智能快递柜管理系统的功能需求、业务规则、非功能需求与约束条件，作为设计、开发、测试与验收的共同依据。文档面向课程设计评审教师、项目组成员与后续维护者。

### 1.2 编写原则

- **可验证**：每条需求都有唯一编号，测试用例可回溯到需求编号；
- **可重现**：所有涉及数量的规则（时长、费率、限额）都写明具体数值，不写"若干""适当"；
- **有边界**：明确说明系统**不做什么**（见第 8 章），避免验收时对范围产生分歧。

### 1.3 术语与缩写

| 术语 | 说明 |
|---|---|
| 触屏端 / 柜机端 | 安装在快递柜上的触摸屏界面，默认首页，路径 `/` |
| 手机端 / H5 | 用户手机浏览器访问的移动页面，路径 `/m` |
| 管理端 / 后台 | 管理员使用的 Web 看板，路径 `/admin` |
| 格口（Cell） | 快递柜中一个可独立开关的储物格，是资源分配的最小单位 |
| 取件码 | 6 位纯数字，取件凭证，全局唯一 |
| 运单号 | 14 位，前缀标识业务方向 + 12 位随机数字，全局唯一 |
| 票据（Ticket） | 柜机屏幕上二维码的一次性凭据，128 bit 随机串，2 分钟有效 |
| 柜机会话 | 用户扫码登录后柜机持有的登录态，空闲 2 分钟自动退出 |
| 超时保管费 | 超过免费保管期后按件收取的费用 |
| 幂等键（Idempotency-Key） | 客户端生成的唯一串，用于保证重复请求不会二次开柜 |

## 2. 项目背景与目标

### 2.1 背景

现有快递柜系统只有"触屏端 + 后台"两部分，且两者混在同一个页面入口里：普通用户打开网页即可看到后台入口，不符合真实柜机的使用场景。同时，真实取件流程中"人还在路上就能开柜"的能力缺失——用户必须走到柜机前输入取件码。

### 2.2 建设目标

1. **还原真实柜机形态**：柜机只承担"取件"与"快递员存件"两类高频操作，其余低频操作（寄件、我的包裹、消息通知）迁移到手机端；
2. **端与端彻底分离**：触屏端、手机端、管理端三个入口在路由层面隔离，柜机界面不含任何后台入口；
3. **支持远程取件**：用户可在手机端查看待取包裹并远程开柜，开柜结果由柜机回执确认；
4. **支持扫码登录柜机**：用户与快递员均可扫描柜机屏幕二维码，免输入完成柜机登录。

### 2.3 成功标准

- 从零开始，按《部署与运行手册》操作可在 15 分钟内跑起完整系统；
- 触屏端页面内不存在任何指向管理端的链接或文字；
- 手机端可完成"登录 → 看待取 → 远程开柜 → 收到回执"的完整闭环；
- 扫码登录全流程（建票 → 扫码 → 确认 → 柜机登录）在 HTTP 局域网环境下可用。

## 4. 系统边界与运行环境

### 4.1 系统组成

```
触屏端（柜机浏览器）  ─┐
手机端（手机浏览器）  ─┼─→  Flask 服务端（REST API） ─→ MySQL 8.0
管理端（PC 浏览器）   ─┘                │
                                      └─→ 通知 worker（短信/站内信/推送，演示环境为模拟通道）
```

### 4.2 技术环境

| 项目 | 要求 |
|---|---|
| 服务端 | Python 3.10+，Flask 3.x，PyMySQL，DBUtils 连接池 |
| 数据库 | MySQL 8.0+（使用 CHECK 约束与窗口函数） |
| 前端 | 原生 HTML/CSS/JavaScript，无构建步骤，无第三方框架 |
| 二维码 | 服务端 `segno` 生成 SVG，前端零依赖 |
| 浏览器 | Chrome / Edge 90+，移动端 Safari / Chrome |
| 部署 | Windows 10/11 或 Linux，默认端口 5000 |

### 4.3 不在本系统范围内

- **生产资金通道**：支付已从本清单移出并升级为正式功能（见 FR-I-09～FR-I-12），但**只做到模拟支付与支付宝沙箱两种模式**，不接生产商户号、不做真实扣款与对账；
- 真实短信网关（演示环境验证码直接回显，生产需接入运营商通道）；
- 物理柜体驱动（柜门开关由 `t_device_command` 指令队列模拟，未对接串口/继电器）；
- 人脸识别、身份证核验等实名认证能力；
- 地图室内导航与步行路径规划（只做直线距离 Haversine 与加权推荐，不做路径规划）。

### 4.4 外部依赖与降级要求

系统引入四个外部依赖，**全部要求可降级**：

| 依赖 | 用途 | 不可用时必须 |
|---|---|---|
| DeepSeek API | 智能寄件问答、包装推荐 | 走本地规则引擎，**仍返回 200**，响应体 `degraded: true` |
| 高德 JS API | 浏览器端地图渲染 | 前端降级为"列表 + 示意图" |
| 高德 Web 服务 API | 地理编码 / 逆地理编码 | 降级本地计算，`provider: "local"` |
| 支付宝沙箱 | 支付下单与回调验签 | 自动回落 mock 模式，页面明示"模拟支付" |

**总原则：外部依赖不可用时，业务接口一律返回 200 并带 `degraded: true` + `degraded_reason`，不得返回 500。** 详细契约见 `docs/08` 与 `docs/api-innovations.md`。

## 5. 功能需求

需求编号规则：`FR-<模块>-<序号>`。模块代号：K=触屏端，M=手机端，A=管理端，S=系统服务。

### 5.1 触屏端（柜机）

| 编号 | 需求名称 | 描述 | 优先级 |
|---|---|---|---|
| FR-K-01 | 扫码取件 | 首页常驻展示二维码，内容为手机端深链 `/m?ticket=<32位hex>`；有效期 120 秒，到期显示"已过期"并提供刷新按钮；柜机每 1.5 秒轮询票据状态，手机确认后自动登录并跳转取件页 | 高 |
| FR-K-02 | 扫码会话展示 | 扫码登录成功后，首页二维码区域替换为身份卡（姓名 + 掩码手机号），提供"继续取件/进入工作台"与"退出登录" | 高 |
| FR-K-03 | 空闲自动登出 | 柜机会话在 120 秒内无点击/键盘操作时自动退出登录，回到扫码态 | 高 |
| FR-K-04 | 取件码取件 | 首页输入 6 位取件码，校验通过后开柜并展示格口号；输入非 6 位数字时前端拦截提示 | 高 |
| FR-K-05 | 超时缴费 | 包裹超时时先弹出缴费弹层，展示金额（默认 ¥1.00），确认支付后自动开柜 | 高 |
| FR-K-06 | 开柜引导 | 开柜成功后展示格口号高亮 + 30 秒倒计时，提供"重新开门"按钮 | 中 |
| FR-K-07 | 快递员登录 | 工号 + 手机号双因子登录，两者须同属一名快递员 | 高 |
| FR-K-08 | 存件 | 录入收件人手机号、姓名、规格、重量，系统分配格口并生成取件码；支持关联寄件单（按揽收码/运单号/手机号匹配），关联后锁定规格与重量 | 高 |
| FR-K-09 | 揽收 | 列出本柜待揽收寄件，逐件揽收并开柜 | 高 |
| FR-K-10 | 投递记录 | 按收件人手机号、柜体、时间范围、状态查询本人经手包裹 | 中 |
| FR-K-11 | 柜体切换 | 左上角下拉切换当前柜体，二维码、取件、存件均以所选柜体为准 | 中 |
| FR-K-12 | 使用帮助 | 图文说明扫码取件、输码取件、快递员操作三类流程 | 低 |

**约束**：触屏端不得包含任何指向管理端的入口、链接或文字；不得包含寄件下单、我的包裹、消息通知三类低频功能（已迁移至手机端）。

### 5.4 系统服务

| 编号 | 需求名称 | 描述 | 优先级 |
|---|---|---|---|
| FR-S-01 | 通知入队 | 业务事件（存入、揽收、撤回、取件、超时、异常）自动生成通知记录，按模板渲染标题与正文 | 高 |

| FR-S-06 | 健康检查 | `/api/health` 返回服务与数据库连通状态 | 中 |

## 6. 业务规则

## 7. 非功能需求

### 7.1 性能

| 编号 | 指标 | 目标值 |
|---|---|---|
| NFR-P-01 | 列表接口响应时间（1000 条数据量） | P95 < 500ms |
| NFR-P-02 | 开柜接口响应时间 | P95 < 800ms（含指令入队） |
| NFR-P-03 | 并发查询 | 50 并发持续 60 秒，错误率 < 1% |
| NFR-P-04 | 并发取件 | 20 并发取不同包裹，无重复开柜、无超卖 |
| NFR-P-05 | 柜机轮询开销 | 单柜机轮询间隔 1.5 秒，服务端单次查询走索引，不随柜机数量线性劣化 |

### 7.2 安全

| 编号 | 要求 | 实现手段 |
|---|---|---|
| NFR-S-01 | 管理端不可被普通用户触达 | 服务端 `before_request` 校验 Cookie，未登录 302；页面不含入口；静态资源白名单 |
| NFR-S-02 | 管理端会话不可被脚本窃取 | HttpOnly Cookie + SameSite=Lax，响应体不回传 token |
| NFR-S-03 | 越权访问他人数据 | 所有查询按 token 中的身份过滤，不接受前端传入的手机号/用户 ID |
| NFR-S-04 | 二维码不可重放 | 票据 128 bit 随机、2 分钟过期、`CONFIRMED` 原子消费一次 |
| NFR-S-05 | 重复开柜 | 幂等键唯一索引 + 首次响应快照复用 |
| NFR-S-06 | 密码时序攻击 | `hmac.compare_digest` 比较 |
| NFR-S-07 | 账号清单泄露 | `/api/auth/accounts` 需登录且不返回密码字段 |

### 7.3 可用性与可维护性

| 编号 | 要求 |
|---|---|
| NFR-U-01 | 柜机触摸目标不小于 44×44 px，主操作按钮字号不小于 18px |
| NFR-U-02 | 手机端适配 360~430px 宽度，无横向滚动 |
| NFR-U-03 | 通知发送失败不影响主业务事务（入队与投递解耦） |
| NFR-U-04 | 页面禁止强缓存（HTML `no-store`），避免旧页面残留 |
| NFR-M-01 | 代码通过 pylint 检查，无 error 级问题 |
| NFR-M-02 | 核心业务模块单元测试行覆盖率 ≥ 70% |
| NFR-M-03 | 所有数据库变更以幂等迁移脚本形式提供（`CREATE TABLE IF NOT EXISTS`） |

## 8. 约束与假设

### 8.1 约束

1. **网络约束**：校园网/公共 Wi-Fi 普遍启用 AP 隔离，手机无法直接访问柜机的局域网地址。系统提供内网穿透启动脚本（cloudflared）作为解决方案，但穿透属于部署手段，不属于系统功能。
2. **浏览器约束**：`getUserMedia`（网页调用摄像头）仅在 HTTPS 或 localhost 下可用。因此手机端**不做应用内扫码**，扫码统一走"手机系统相机扫深链"的方式。
3. **演示约束**：支付、短信均为模拟实现，不产生真实资金与短信费用。
4. **数据约束**：演示库含 30 台柜机、720 个格口、310 条包裹、120 名用户、60 名快递员、30 家快递公司。
   （数字以 `init_database.sql` 的种子数据为准，可用 `python scripts/seed_row_counts.py` 复核。）

### 8.2 假设

1. 柜机与服务器之间网络可达（同一局域网或经穿透）；
2. 柜机浏览器常驻前台，不启用省电休眠；
3. 管理员账号由系统预置，不提供自助注册；
4. 快递员账号由管理员建档，不提供自助注册。
