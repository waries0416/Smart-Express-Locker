## 1. 选题背景

### 1.1 现实问题

快递柜是一个**三端并存**的产品形态，但多数课程作业只做了其中一端：

| 端 | 真实形态 | 常见作业做法 |
|---|---|---|
| 柜机触屏端 | 装在柜体上，屏幕固定、无人值守、只有取件与快递员存件 | 和后台混在同一个网页里 |
| 手机端 | 用户提前操作，减少柜前输入 | 省略，或做成"网页版后台" |
| 管理端 | 运营方看板与基础数据维护 | 唯一实现的端 |

本项目要解决三个具体痛点：

1. **柜前输入成本高**：6 位取件码要在触摸屏上逐位点，老人和抱小孩的人尤其不便；
2. **端与端没有边界**：普通用户打开网页就能看到后台入口，不符合真实柜机场景；
3. **远程能力缺失**："人还在路上就能开柜"这件事做不了，必须走到柜机前。

### 1.2 建设目标

| 编号 | 目标 | 可验证的成功标准 |
|---|---|---|
| O-1 | 还原真实柜机形态 | 触屏端页面内**不存在**任何指向管理端的链接、按钮或文字 |
| O-2 | 端与端路由层隔离 | 未登录访问 `/admin/dashboard` 由**服务端 302** 拦截，关掉 JS 也挡得住 |
| O-3 | 支持远程取件 | 手机端完成"登录 → 看待取 → 远程开柜 → 收到回执"闭环 |
| O-4 | 支持扫码登录柜机 | 建票 → 扫码 → 确认 → 柜机登录 全流程在 HTTP 局域网可用 |
| O-5 | 从零可复现 | 按《部署与运行手册》操作可跑起完整系统，且每步都有预期输出 |
| O-6 | 有工程化质量证据 | 单元测试、覆盖率、静态检查、性能剖析、并发压测五项均有原始输出 |

> O-6 是**本轮（第二轮）新增**的目标。第一轮只有功能与手工测试，没有工具链证据。

### 1.3 范围边界

明确**不做**的事，避免验收时对范围产生分歧（详见 `docs/01` §8、`docs/03` §7）：

- 不驱动真实柜门硬件（开柜动作以指令队列 `t_device_command` 模拟）；
- 不接真实短信通道（验证码走开发模式回显）；
- 不做实名认证（人脸、身份证核验）。

本轮把"支付"从边界外**移回**边界内，但只做到"模拟支付 + 支付宝沙箱"，不接生产资金通道。

## 2. 开发计划

### 2.1 两轮迭代的划分

项目实际分两轮推进。第一轮打通业务主链路，第二轮补创新功能与工程化证据。

| 轮次 | 目标 | 主要产出 | 证据 |
|---|---|---|---|
| 第一轮 | 三端分离 + 主业务闭环 | `backend/` 9 个模块、`frontend/` 三端页面、`db/` 建表与对象脚本、`docs/01`–`06` | `git log` 初始提交 `9ef5a9a`（2026-11-17 21:27）；`docs/01`–`06` 版本头均标 v1.0 / 2026-11-17 |
| 第二轮 | 4 组创新功能 + 质量证据 + 答辩材料 | DeepSeek 智能寄件、包装协同、高德找柜、支付宝沙箱支付；`quality/reports/`；`docs/00`/`07`/`08`/`09`；`deliverables/` | 本轮团队任务 DAG；`docs/api-innovations.md` v1.0（2026-11-18） |

> **必须如实说明的一点**：仓库的 `git log` 只有一个初始化提交，看不到逐日提交历史。
> 因此本文的"迭代"划分依据是**文档版本头 + 缺陷记录 + 本轮任务分派**，而不是提交时间线。
> 答辩若被问"你们的迭代证据在哪"，正确回答是"证据是缺陷记录与文档版本，不是 git 提交粒度"，不要编造提交记录。

### 2.2 第一轮：四个版本的功能切分

按"先能跑、再能看、后能扛、最后加彩"的顺序推进，每个版本都有明确的可演示增量：

| 版本 | 主题 | 完成内容 | 可演示点 |

### 2.3 第二轮：按依赖排的任务图

第二轮不再是"从头写"，而是在既有代码上**加装**，所以必须先定契约再并行：

           Ran 32 tests）；当前口径是 202 条（02_unittest_run2.txt），不要混用。
        │
        ├──────────────┬──────────────┐
        ▼              ▼              ▼
T1 后端创新        T2 三端前端       （T4a 文档骨架，可与 T1/T2 并行）
DeepSeek/包装/高德/支付   页面与交互
        │              │
        └──────┬───────┘
               ▼
      T3-final 质量证据（全量测试/覆盖率/pylint/cProfile/压测/E2E/截图）
               │
               ├──────────────┐
               ▼              ▼

关键决策：**先立契约、再并行**。
`docs/api-innovations.md` 在 T0 阶段就冻结了字段名、状态码、错误码、降级行为，前后端各自照做，联调时只对契约不对人。这是本轮唯一一次"返工成本前置"，事后证明有效——前端按 `provider_label`/`degraded` 字段直接渲染角标，不需要中途改协议。

## 3. 迭代过程中的问题与解决

> 本节只写**真实发生过**的问题。前 5 条来自 `docs/04` §8 的缺陷记录，后 3 条来自本轮 T0/T4a 阶段的实测。

### 3.1 D-01 取件码取件绕过超时保管费（严重：高，资损）

| 项 | 内容 |
|---|---|
| 发现方式 | L2 端到端核验，TC-K-03a 首跑返回 200 而非 402 |
| 根因 | `/api/business/pickup` 只判 `PICKED`/`RETURNED`/`EXCEPTION` 三态，漏了"`EXPIRED` 且未缴费"；而同文件的 `_do_unlock` 有这道判断，**两条取件路径规则不一致** |
| 为什么严重 | 一旦置 `PICKED`，包裹就脱离 `EXPIRED`，`pay-overtime` 的 `status='EXPIRED'` 过滤再也匹配不到它，**这笔账永久收不回** |
| 修复 | 在置 `PICKED` **之前**加闸门，返回 402 + `package_id` + `overtime_fee`；前端捕获 402 后弹缴费层，支付成功用同一取件码自动重试 |
| 回归 | `tests/test_pickup_payment_gate.py` 3 条 |
| 教训 | **同一业务规则出现在两条代码路径上，就一定会分叉。** 要么合并成函数，要么给两条路径都写用例 |

### 3.2 D-02 实体写接口无任何鉴权（严重：高，越权）

| 项 | 内容 |
|---|---|
| 发现方式 | 写测试用例时追问"如果绕过页面直接打接口会怎样" |
| 复现 | 未登录 `curl -X DELETE /api/packages/1` → 直接删库成功 |
| 根因 | 门禁装在**页面**（`before_request` 拦 `/admin/*`）上，没装在**接口**（`/api/*`）上 |
| 修复 | `entities.py` 加 `_guard_mutations`：`POST/PUT/DELETE/PATCH` 校验后台会话；`GET` 保持开放（触屏端投递记录、手机端选柜体依赖 GET） |
| 回归 | `test_route_separation.py` 新增 3 条 |
| 教训 | "页面挡住了"不等于"接口挡住了"。**凡是前端的限制，都是建议；只有服务端的限制才是限制** |

### 3.3 D-03 `[hidden]` 属性失效导致登录条常显（一般：中）

根因是 CSS 优先级：浏览器默认 `[hidden] { display: none }` 打不过类选择器 `.login-bar { display: flex }`。
修复：样式表顶部加 `[hidden] { display: none !important; }`。
**教训：这是"看起来是 JS 的 bug、实际是 CSS 的 bug"的典型，排查时先看计算样式，别急着读逻辑。**

### 3.4 D-04 触屏端可退回旧门户页（一般：中）

两处叠加：旧 `/index.html` 仍在磁盘上可被历史链接访问；HTML 响应未禁缓存，浏览器回退直接读缓存。
修复：删门户页、`/` 与 `/kiosk` 统一指向 `kiosk.html`、旧 URL 302、`after_request` 给 HTML 加 `no-store`。
**教训：删了文件不等于删了入口，还得管住缓存和书签。**

### 3.5 D-05 手机端"扫一扫取件"与柜机票据功能重复（低）

二维码语义从"取件码"改为"登录票据"后，手机端应用内扫码成了重复入口，且受 `getUserMedia` 的 HTTPS 限制实际不可用。
处理：删除相关卡片、浮层、三个函数与配套 CSS，保留系统相机扫码主路径。
**教训：功能重复不可怕，可怕的是重复的那个还不能用。**

### 3.6 契约与实现分叉：鉴权头写成 `X-Kiosk-Token`，代码读 `Authorization: Bearer`（已闭环）

| 项 | 内容 |
|---|---|
| 现象 | `docs/api-innovations.md` §0.2 原本规定用户/快递员凭据放 `X-Kiosk-Token` 请求头；`backend/auth.py` 的 `kiosk_identity()` 实际读的是 `Authorization: Bearer` |
| 影响 | 前端若照契约实现，所有手机端鉴权接口返回 401 |
| **裁决** | **统一 `Authorization: Bearer <token>`，废弃 `X-Kiosk-Token`**（Lead，2026-11-18） |
| 裁决理由 | ① 它是仓库原有的、正在运行的鉴权，触屏/管理/H5 既有接口与全部回归测试都依赖它；② 改文档的风险远低于改运行代码，鉴权是安全边界、回归面最大；③ `docs/02` §7.2 与 `docs/03` §3 原本就写的 `Bearer`，只有契约 1 份写错，按"以代码为准 + 少数服从多数"应改契约 |
| 例外 | `POST /api/pay/notify/alipay` **不带用户 token**，靠 RSA2 签名验签——服务端到服务端回调不存在"用户登录态"；`/api/device/*` 柜机接口仍无鉴权，属**已知未修欠账**，不是本裁决的例外设计 |
| 闭环动作 | `docs/api-innovations.md` 由 backend-engineer 同步；前端统一只发 `Authorization: Bearer`；`docs/00`/`07` 已由 docs-defense 同步 |
| 教训 | **契约文档写"用什么"，必须先回读一遍既有代码里的既有约定。** 这次是契约写错了，不是代码写错了——而且"写错的文档要求改正确的代码"是本可以避免的返工 |

### 3.7 `db/objects.sql` 未被视作必选步骤（本轮）

| 项 | 内容 |
|---|---|
| 现象 | 只跑 `init_database.sql` 后，`GET /api/packages/<id>/detail` 报 `Table 'smart_locker.v_package_detail' doesn't exist` |
| 连带 | 触发器 `trg_package_after_update` 缺失 → 取件后格口不释放 → `test_pickup_succeeds_after_payment` 失败（`'OCCUPIED' != 'FREE'`） |
| 根因 | `init_database.sql` 头注释写"包含所有表结构 + 全量数据"，容易让人以为一步到位；视图/触发器/存储过程实际在 `db/objects.sql` |
| 修复 | `docs/05` §3 与 `docs/04` §5.1 均改为**硬性前置检查**（views=2 / triggers=1 / procs=3），`docs/00` §3 单列一节 |
| 教训 | **"能跑通"的前提条件必须前置显式化**。文档里写"会出两个症状"是描述后果，不是阻止犯错 |

### 3.8 并行开发期间共享数据库的观测漂移（本轮）

现象：同一条 `SELECT COUNT(*) FROM t_package`，十分钟内先看到 313、再看到 310。
原因：多个成员同时对同一个本地 MySQL 执行重置脚本与测试。

处置：
1. 采集"基线数字"时改为**直读 `init_database.sql`**（`scripts/seed_row_counts.py`），不读运行库；
2. 运行库只用于"当前是否健康"的判断；
3. 任何写入型验证先在 `docs/09` 的复现清单里标明占用时间，避免互相踩。

**教训：多人共用一套环境时，"数字"必须绑定"采集时刻 + 采集方式"，否则结论不可复现。**

## 4. 复盘：做对了什么

| # | 做法 | 具体体现 | 效果 |
|---|---|---|---|
| 1 | 先立契约再并行 | `docs/api-innovations.md` 冻结字段/状态码/降级行为 | 前后端联调只对契约，无协议返工 |
| 2 | 规则写进数据库 | 36 条 CHECK、15 条外键、10 条唯一键 | 测试构造错误数据时被真实拦截（改 `expire_time` 触发 `chk_pkg_time`），反向证明约束有效 |
| 3 | 幂等与一次性消费 | 票据 `CONFIRMED` 原子消费、开柜 `Idempotency-Key` | 重复提交不会二次开柜、票据不可重放 |
| 4 | 降级显式化 | `degraded` + `degraded_reason` 字段 | 外部依赖挂了页面仍可用，且用户知道"现在是规则推荐不是 AI" |
| 5 | 缺陷都配回归用例 | D-01、D-02 修复后各加测试 | 同类问题不会二次出现 |

## 5. 复盘：做得不够的地方

| # | 问题 | 证据 | 改进 |
|---|---|---|---|
| 1 | 提交粒度太粗 | `git log` 只有一个初始化提交 | 按 feat/fix 拆分提交，一个提交一件事 |
| 2 | 文档数字写完不回填 | `docs/00` 的 G-01～G-04 | 数字一律由脚本生成，不做手工抄写 |

| 5 | 共享环境影响可复现性 | 行数漂移 | 基线数字直读种子脚本，不读运行库 |

## 6. 答辩可用的一句话总结

> 这个系统做对的核心是一件事：**把"边界"当设计对象来做**——端与端的边界用服务端路由门禁守住，规则的边界写进数据库约束，外部依赖的边界用 `degraded` 显式暴露，团队的边界用一份冻结的 API 契约隔开。
> 做错的地方也很典型：文档数字靠手抄、前置条件靠口传，这两件事最后都变成了答辩现场会被追问的点。
