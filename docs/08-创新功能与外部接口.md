## 0. 四组创新一览

| 组 | 名称 | 解决的现实问题 | 外部依赖 | 无依赖时 |
|---|---|---|---|---|
| I-1 | DeepSeek 智能寄件问答与包装推荐 | 用户不知道自己的东西能不能寄、要怎么包、要多大格口 | DeepSeek API | 本地规则引擎，仍返回 200 |
| I-2 | 包装准备协同 | 快递员到柜才发现没带气泡膜/纸箱，白跑一趟 | 无（内部功能，依赖 I-1 的输出） | 不适用 |
| I-3 | 高德地图找柜与智能选柜 | 用户不知道最近的柜子在哪、哪个柜子有空位 | 高德 JS API + Web 服务 API | 按 `cabinet_id` 排序，`distance_m: null` |
| I-4 | 支付宝沙箱 / 模拟支付 | "点一下就算付了"没有真实支付链路，无法演示完整流程 | 支付宝沙箱（RSA2） | 默认 mock，页面醒目提示"模拟支付" |

**贯穿四组的一条统一原则**（也是答辩最该讲的一句）：

> **外部依赖挂了，业务不能挂。** 四组创新接口在任何外部依赖不可用时，一律降级为 200 成功返回，并在响应体里用 `degraded: true` + `degraded_reason` 明示原因，绝不返回 500。

## 1. I-1 DeepSeek 智能寄件问答与包装推荐

### 1.1 需求来源

现有寄件流程要求用户自己回答三个他答不上来的问题：

| 用户被要求回答 | 真实困难 |
|---|---|
| 这东西能寄吗？ | 不知道哪些是禁运品（锂电池、香水、刀具…） |
| 该选小件还是中件？ | 不知道自己的东西折算成体积对应哪个格口 |
| 怎么包？ | 不知道要不要气泡膜、要不要易碎标签 |

结论：这三个问题应由系统给出建议，而不是让用户填空。

### 1.2 两个接口

#### `GET /api/ai/health` — 能力探测（公开）

用途：前端据此决定要不要显示"AI 推荐"角标。**只回布尔，绝不回 Key。**

```json
{ "provider": "deepseek", "configured": true, "mode": "deepseek" }
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `configured` | boolean | 服务端是否读到 `DEEPSEEK_API_KEY` |
| `mode` | `"deepseek" \| "rule"` | 当前实际生效模式 |

#### `POST /api/ai/pack-recommend` — 包装推荐（公开 + 频控）

请求：`{ "description": "一个玻璃杯和两本书" }`，去空白后 1–500 字符。

响应（节选关键字段）：

```json
{
  "source": "deepseek",
  "elapsed_ms": 812,
  "degraded": false,
  "degraded_reason": null,
  "forbidden": [ { "name": "锂电池", "reason": "航空禁运" } ],
  "sensitive": [ { "name": "玻璃杯", "reason": "易碎需缓冲" } ],
  "packaging": [ { "step": 1, "title": "气泡膜包裹", "detail": "玻璃杯至少包 3 层" } ],
  "size_type": "MEDIUM",
  "size_reason": "两本书+玻璃杯体积中等，需留缓冲空间",
  "materials": [ "气泡膜", "5 号纸箱", "易碎标签" ],
  "notice": "结果仅供参考，以快递员/承运商审核为准",
  "recommendation_id": 15
}
```

字段约定：

| 字段 | 约束 |
|---|---|
| `source` | **只能是 `"deepseek"` 或 `"rule"`**，前端据此显示"AI 推荐"/"规则推荐"角标 |
| `size_type` | 必须落在 `t_cell.size_type` 取值域内：`SMALL / MEDIUM / LARGE` |
| `packaging[].step` | 从 1 连续递增 |
| `notice` | **固定文案，含"以快递员/承运商审核为准"，前端必须原样展示** |
| `recommendation_id` | 本轮新增字段（向后兼容），供 I-2 引用 |

#### `POST /api/ai/chat` — 智能问答（公开）

请求 `{ "message": "超时了怎么取件？" }`，响应 `{ source, reply, session_id, elapsed_ms, degraded, degraded_reason }`。
**无状态实现**：`session_id` 仅用于前端串联对话，服务端不存会话。

### 1.3 关键设计：模型只给建议，服务端说了算

这是本组最值得讲的一个设计决策。

| 风险 | 若不处理 | 本项目的处理 |
|---|---|---|
| 模型返回 `size_type: "XL"` | 前端拿去做格口分配，SQL 匹配不到，静默失败 | 用 `packaging_rules.py` 做**枚举修正**，强制落回三档 |
| 模型漏掉禁运品 | 用户寄了锂电池，出安全事故 | **禁寄词强制补全**：本地词表命中即追加，不依赖模型 |
| 模型返回 0 步或 20 步打包流程 | 页面渲染崩坏 | 步骤数**上下限**裁剪 |
| 模型返回非 JSON | 解析异常 → 500 | 严格 Schema 校验，不合法即视为失败 → 降级本地规则 |

一句话：**模型的输出是"草稿"，落到响应体里的结构是服务端校验后的结果。**

### 1.4 安全约束

| 要求 | 实现 |
|---|---|
| Key 不泄露 | `DEEPSEEK_API_KEY` 只从环境变量读，**永不出现在响应、日志、错误信息**；日志打印请求头一律脱敏为 `sk-***` |
| 超时与重试 | 默认 8s（`DEEPSEEK_TIMEOUT`），最多重试 2 次；**只对超时/5xx/429 重试**，4xx 不重试 |
| 频控 | 超频返回 429 `RATE_LIMITED` + `retry_after_s` |
| 不自动下单 | 禁寄/敏感只做**提示**，绝不自动确认订单 |

### 1.5 环境变量

| 变量 | 默认 | 可下发前端 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 空 | ❌ |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` | ❌ |
| `DEEPSEEK_MODEL` | `deepseek-chat` | ❌ |
| `DEEPSEEK_TIMEOUT` | `8` | ❌ |
| `DEEPSEEK_MAX_RETRY` | `2` | ❌ |
| `AI_ENABLED` | `1` | — |

## 2. I-2 包装准备协同

### 2.1 需求来源

I-1 只解决了"用户知道怎么包"，但真正的断点在**快递员这一侧**：

> 快递员到柜取件，才发现这单需要气泡膜 + 5 号纸箱，而车里没有 → 白跑一趟 → 要么现场糊弄，要么回站再跑。

本组把 I-1 的推荐结果**转成快递员可执行的备包装任务**，并给他一份材料台账。

### 2.2 数据模型

| 表 | 作用 |
|---|---|
| `t_pack_material` | 材料台账：名称、规格、库存、低库存阈值、单位 |
| `t_pack_task` | 备包装任务：关联包裹、指派快递员、状态 |
| `t_pack_task_item` | 任务所需的材料明细（**数量快照**） |
| `t_package.pack_recommendation_id` | 新增可空列，把寄件单和推荐结果关联起来 |

**为什么材料名/数量要在任务行内快照？**
材料台账后续改名或改单位，不能把历史任务里的"气泡膜 1 卷"变成别的东西。快照让历史任务与台账解耦。

### 2.3 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/pack-materials` | COURIER 或 admin | 全量台账；`stock <= threshold` 前端标红 |
| PUT | `/api/pack-materials/{id}` | COURIER 或 admin | 只接受 `stock`、`threshold`；`stock` 为整数且 `0 <= stock <= 100000` |
| GET | `/api/courier/packaging-tasks` | COURIER（本人）或 admin | 快递员只看 `assignee_courier_id = 本人`；越权 403 |
| POST | `/api/courier/packaging-tasks/{id}/done` | COURIER（本人）或 admin | 完成；非本人 403，已完成/已取消 409 |

任务列表响应节选：

```json
{ "count": 1, "page": 1, "size": 20,
  "data": [ { "task_id": 7, "package_id": 319, "tracking_no": "SF1234567890",
              "cabinet_code": "CAB-002", "cell_code": "A01",
              "size_type": "MEDIUM", "status": "PENDING",
              "materials": [ { "name": "气泡膜", "qty": 1, "unit": "卷" } ] } ] }
```

### 2.4 状态机

```
PENDING ──done──> DONE
   │
   └──cancel──> CANCELED
```

已完成或已取消的任务再调 `done` → 409 `CONFLICT`，不重复记账。

### 2.5 与 I-1 的衔接

```
用户提交寄件描述
      │
      ▼
POST /api/ai/pack-recommend  ──> 返回 recommendation_id
      │
      ▼
寄件请求带可选字段 pack_recommendation_id
      │  （缺失时行为与改造前完全一致）
      ▼
t_package.pack_recommendation_id
      │
      ▼
自动生成 t_pack_task + t_pack_task_item（材料数量快照）
      │
      ▼
快递员 GET /api/courier/packaging-tasks 领取任务
```

**向后兼容要点**：`pack_recommendation_id` 是可选字段，不传时整套流程退化回原样。这保证了老接口和老页面不受影响。

## 3. I-3 高德地图找柜与智能选柜

### 3.1 需求来源

原 `GET /api/m/cabinets/nearby?q=` 只能按编号/位置**模糊搜索**，用户的实际问题是：

1. 我在哪？最近的柜子有多远？
2. 那个柜子还有大格口吗？（有柜子但没合适格口，等于没有）

### 3.2 在既有接口上增补（不新建接口）

`GET /api/cabinets/nearby` 保留**全部原有字段与原有排序**，只增补：

| 新增字段 | 类型 | 说明 |
|---|---|---|
| `latitude` / `longitude` | number \| null | 柜体坐标；未维护时为 `null` |
| `distance_m` | integer \| null | Haversine 直线距离（米，四舍五入） |
| `score` | number \| null | 可用格口加权得分（0–1） |
| `recommended` | boolean | 本次结果中得分最高者，**仅 1 个为 true** |

顶层新增：`degraded`、`degraded_reason`、`sorted_by`（`"distance+availability"` 或 `"cabinet_id"`）。

### 3.3 排序规则

| 情况 | 排序 |
|---|---|
| 有 `lat`/`lng` | `score` 降序 → `distance_m` 升序 → `cabinet_id` 升序 |
| 无坐标（降级） | 维持 `cabinet_id` 升序，**与改造前完全一致** |
| 部分柜体无坐标 | 无坐标者排末尾（`distance_m: null`），不影响其它柜顺序 |

**为什么要保留 `cabinet_id` 兜底排序？**
改造前的老页面、老书签、老测试用例都依赖这个顺序。降级时顺序不变，老用例就不会假失败。

### 3.4 参数校验与降级

| 输入 | 结果 |
|---|---|
| `lat`/`lng` 非数字、纬度超 ±90、经度超 ±180 | 400 `BAD_REQUEST` |
| 坐标合法，但**所有柜体都没有坐标** | 200 + `degraded: true` + `degraded_reason: "柜体坐标未维护"` |
| 没传坐标 | 200，按 `cabinet_id` 排序，`distance_m: null` |

### 3.5 地址解析 `GET /api/location/resolve`

| 情况 | 响应 |
|---|---|
| 有 `AMAP_WEB_KEY` 且可用 | `provider: "amap"`，`location` 含经纬度与格式化地址、省市区，附带 `nearest_cabinets` |
| 无 Key / 无网络 | `provider: "local"`，`degraded: true`，`location: null`，`nearest_cabinets` 仍按本地柜体坐标计算 |
| `address` 与 `lat/lng` 都没给 | 400 `BAD_REQUEST` |

### 3.6 Key 分级（安全红线）

这是本组最容易出安全事故的地方，必须讲清：

| 环境变量 | 用途 | 能否下发到前端 |
|---|---|---|
| `AMAP_JS_KEY` | JS API 2.0 浏览器端加载地图 | ✅ 可以，**但必须先在控制台配置域名白名单** |
| `AMAP_JS_SECURITY_CODE` | JS API 2.0 安全密钥 | ✅ 可以，同上需绑定域名 |
| `AMAP_WEB_KEY` | Web 服务 API（地理编码/POI） | ❌ **永远只在服务端，禁止出现在任何响应、日志、前端代码里** |

`GET /api/map/config` 只下发前两个；对 `AMAP_WEB_KEY` **只回一个布尔** `web_service_available`。

一句话：**浏览器端 Key 可以公开（有域名白名单兜底），服务端 Key 一旦泄露就是计费损失。**

## 4. I-4 支付宝沙箱 / 模拟支付

### 4.1 需求来源

原实现是"点击'我已支付'即视为成功"——这在演示时最难解释的一句话就是"那你怎么证明它真的收到钱了"。
本组把支付做成**真实的订单模型**，只是资金通道可选沙箱或模拟。

### 4.2 订单模型

| 表 | 作用 |
|---|---|
| `t_pay_order` | 支付单：商户订单号、金额**快照**、渠道、状态、过期时间 |
| `t_pay_callback_log` | 回调日志：支付宝异步通知原文、验签结果 |

状态机：

```
PENDING ──支付成功──> SUCCESS
   │                    │
   ├──超时/主动关──> CLOSED
   └──支付失败────> FAILED
```

### 4.3 五类接口

| 方法 | 路径 | 权限 | 要点 |
|---|---|---|---|
| POST | `/api/pay/create` | USER（本人包裹）或 admin | 幂等：同 `biz_type`+`biz_id` 有未过期 `PENDING` 单则**复用原单** |
| GET | `/api/pay/{pay_id}` | USER（本人）/ COURIER（相关）/ admin | — |
| POST | `/api/pay/{pay_id}/mock-succeed` | admin 且 mock 模式 | 非 mock 模式 → 403 `MOCK_NOT_ALLOWED` |
| POST | `/api/pay/notify/alipay` | 公开但需 RSA2 验签 | 成功返回**纯文本 `success`**（支付宝要求，不能是 JSON） |
| GET | `/api/pay/records` | admin | 支付流水，支持 page/size/status/provider/biz_type |

### 4.4 三条防刷设计

| 攻击面 | 设计 |
|---|---|
| 前端改金额 | **服务端金额快照**：金额由后端按 `biz_type`+`biz_id` 重算写入 `t_pay_order.amount`；请求里带 `amount` **一律忽略** |
| 重复回调 | `(pay_no, trade_no)` 唯一键；重复通知只记日志不重复入账，仍返回 `success` |
| 重复提交 | 同业务单已有未过期 `PENDING` 单则复用；模拟支付重复调用返回 `idempotent: true`，`paid_at` 保持首次值 |

### 4.5 支付闸门（保持不变，且更强了）

超时未缴费的取件**仍然**被 402 拦截：

```json
{ "error": "NEED_PAYMENT", "package_id": 319, "amount": 1.00, "message": "..." }
```

只有同时满足三个条件的支付单存在时才放行：`biz_type=OVERTIME` **且** `biz_id=该 package_id` **且** `status=SUCCESS`。

> **绝不相信前端传来的"已支付"标记或金额。**

这条正好呼应 D-01 缺陷：原来的问题是"页面弹了缴费层，但接口没拦"，现在接口侧有了独立于页面的资金凭证校验。

### 4.6 mock 模式的显式化

`PAYMENT_PROVIDER=mock`（默认）时，**所有接口、页面、响应**都必须带：

- `mock: true`
- `provider_label: "模拟支付"`
- 页面上醒目的"模拟支付，不产生真实扣款"标识

`alipay` 模式需要 `ALIPAY_APP_ID` / `ALIPAY_PRIVATE_KEY` / `ALIPAY_PUBLIC_KEY` 齐全且 `ALIPAY_SANDBOX=1`；**缺凭据时自动回落 mock 并置 `degraded: true`，绝不尝试真实扣款。**

**为什么这么设计？** 因为"把 mock 误当成真付"是这类项目最危险的状态。让 mock 处处可见，比任何注释都有效。

## 5. 外部接口总览（答辩速查表）

| 外部服务 | 用途 | 凭据变量 | 不可用时的行为 | 数据外发内容 |
|---|---|---|---|---|
| DeepSeek | 包装推荐、智能问答 | `DEEPSEEK_API_KEY` | 降级本地规则，200 + `degraded` | **用户输入的物品描述文本** |
| 高德 JS API | 浏览器端地图渲染 | `AMAP_JS_KEY` + `AMAP_JS_SECURITY_CODE` | 前端降级为"列表 + 示意图" | 用户浏览器定位（需用户授权） |
| 高德 Web 服务 | 地理编码 / 逆地理编码 | `AMAP_WEB_KEY` | 降级本地计算，200 + `degraded` | 用户输入的地址文本 |
| 支付宝沙箱 | 支付下单与回调验签 | `ALIPAY_*` | 回落 mock，200 + `degraded` | 商户订单号、金额 |

> **隐私提示（答辩可能被问）**：AI 推荐会把用户输入的物品描述发给 DeepSeek。因此本项目**不得**把收件人姓名、手机号、地址拼进该请求体 —— 只发物品描述本身。这一点在契约里以"请求体只有 `description`"的形式约束住了。

## 6. 降级矩阵（一页看懂"外部挂了会怎样"）

| 能力 | 有凭据且可用 | 无凭据 | 调用失败 |
|---|---|---|---|
| AI 包装推荐 | `source: "deepseek"`, `degraded: false` | `source: "rule"`, `degraded: true` | 同左 |
| AI 问答 | `source: "deepseek"` | `source: "rule"`（本地 FAQ 规则表） | 同左，仍 200 |
| 地图找柜 | 带 `distance_m`，按距离+空闲加权排序 | 按 `cabinet_id` 排序，`distance_m: null`，`degraded: true` | 同左 |
| 地址解析 | `provider: "amap"` | `provider: "local"`, `location: null` | 同左 |
| 支付 | `provider: "alipay_sandbox"` | `provider: "mock"`, `mock: true`，页面明示 | 回落 mock |

**统一错误码表**（四组创新共用）：

| HTTP | code | 含义 |
|---|---|---|
| 400 | `BAD_REQUEST` | 参数缺失/类型错误/超长 |
| 400 | `VALIDATION_FAILED` | 业务校验不通过 |
| 401 | `UNAUTHORIZED` | 未登录 / token 缺失或签名错误 / 过期 |
| 403 | `FORBIDDEN` | 已登录但无权操作该资源 |
| 403 | `ROLE_REQUIRED` | 需要特定角色（响应带 `required_role`） |
| 404 | `NOT_FOUND` | 资源不存在 |
| 409 | `CONFLICT` | 幂等冲突 / 状态不允许 |
| 429 | `RATE_LIMITED` | 触发频控（AI 接口） |
| 500 | `INTERNAL_ERROR` | 服务端异常，**不应由业务输入触发** |
| 503 | `UPSTREAM_UNAVAILABLE` | 外部依赖不可用**且**本地兜底也失败（正常不会出现） |

## 8. 答辩口径（三句话讲完四组创新）

1. **AI 那组**：我们不让模型直接决定业务结果——模型的输出会被本地规则二次校验（枚举修正、禁寄词强制补全、步骤数裁剪），模型只是"起草"，落库的结构是服务端说了算。
2. **协同那组**：AI 帮用户算出要什么包装，我们把这份清单变成快递员的备包装任务和材料台账，形成"用户 → 系统 → 快递员"的闭环，而不是止于一句建议。
3. **地图和支付那两组**：共同点是**外部依赖一律可降级**——高德没 Key 就按柜号排，支付宝没凭据就回落模拟支付并在页面上写清楚，任何情况下都不会因为外部服务挂了而让业务返回 500。
