## 1. 设计目标与原则

### 1.1 目标

把需求规格说明书中的 12 个触屏端需求、12 个手机端需求、7 个管理端需求、6 个系统服务需求，落实为一套可运行、可维护、可演示的软件结构。

### 1.2 原则

| 原则 | 落地做法 |
|---|---|
| **单一入口、多端隔离** | 一个 Flask 进程同时服务三个端，但页面路由在服务端分离，柜机页面物理上不含后台入口 |
| **业务逻辑只写一遍** | 手机端开柜复用 `business.do_unlock()`，不另写一套状态机；身份签发复用 `auth.issue_kiosk_token()` |
| **身份只认 token** | 服务端从 token 解析 `(role, rid)`，不接受前端传手机号/用户 ID，从结构上杜绝越权 |
| **失败不阻塞主流程** | 通知入队与投递解耦；开柜指令入队与执行解耦 |
| **可演示即可解释** | 每个"看起来多余"的设计都在代码注释里写清原因（如为什么不用网页摄像头） |
| **零构建前端** | 不用 npm / 打包器，浏览器直接跑，降低部署与评审门槛 |

## 4. 技术选型与理由

| 决策点 | 选择 | 理由 | 放弃的方案及原因 |
|---|---|---|---|
| 后端框架 | Flask | 轻量、蓝图天然适合按端拆分、课程已使用 | Django：ORM 与 admin 会掩盖 SQL 设计，不利于展示数据库能力 |
| 数据库 | MySQL 8.0 | 支持 CHECK 约束、窗口函数、生成列；课程要求 | SQLite：并发写与 CHECK 支持弱，无法体现事务与行锁 |
| 数据访问 | 原生 SQL + PyMySQL | 每条 SQL 都可写进文档，索引与执行计划可见 | SQLAlchemy：抽象层会隐藏 SQL，答辩时说不清"为什么慢" |
| 连接管理 | DBUtils PooledDB | 通知 worker 与请求线程共享池，避免频繁建连；借出时 ping 自动剔除死连接 | 每次新建连接：柜机 1.5 秒轮询会把 MySQL 连接数打满 |
| 前端 | 原生 JS | 零构建、可直接在柜机浏览器打开、评审可读 | Vue/React：需要 node 环境与打包步骤，增加"照之能重现"的成本 |
| 二维码 | segno（服务端出 SVG） | 纯 Python 无 Pillow 依赖；SVG 矢量清晰；前端零依赖 | 前端 qrcode.js：多一个库；Pillow：Windows 装编译依赖麻烦 |
| 管理端会话 | HttpOnly Cookie | 服务端渲染页面前就能校验，未登录直接 302，关掉 JS 也挡得住 | sessionStorage token：必须靠前端 JS 跳转，脚本禁用即失效 |
| 手机端扫码 | 系统相机扫深链 | `getUserMedia` 仅 HTTPS/localhost 可用，局域网 HTTP 直接禁用 | 应用内摄像头扫码：演示环境必然失败 |
| 手机远程开柜 | 指令队列 + 柜机回执 | 手机无法直连柜机；队列可重放、可审计、可幂等 | 手机直接改数据库状态：无法确认柜门是否真开，异常无法排查 |

## 5. 关键设计决策

### 5.1 路由分离：服务端门禁，而不是前端跳转

**问题**：原系统只有一个 `index.html`，用户能"返回首页"摸到门户页，进而看到后台入口。

**方案**：

1. 删除门户页 `index.html`；
2. `/` 与 `/kiosk` 直接返回 `kiosk.html`；
3. 管理端挂独立前缀 `/{ADMIN_PATH}`（默认 `admin`，可用环境变量改）；
4. `@app.before_request` 拦截 `GET /admin/*`（登录页除外），无有效 Cookie 直接 `302`；
5. 静态资源白名单只放行 `css/js/lib/img` 四个目录，`/admin.html` 这类旧地址一律 302，未知路径 404（不回退首页）。

**取舍**：门禁放在服务端，前端即使被改也无济于事；代价是每次页面请求多一次 HMAC 校验（微秒级，可忽略）。

### 5.2 扫码登录：票据换 token，而不是二维码里塞身份

**问题**：二维码若直接编码用户身份，被拍照即等于泄露账号。

**方案**：引入一次性票据 `t_qr_ticket`。

```
柜机 POST /api/qr/ticket        → 生成 128bit 随机票据，返回深链 /m?ticket=xxx
手机 扫深链                     → GET /api/qr/ticket/xxx 读取柜机信息
手机 点确认                     → POST .../confirm（带手机 token，只认 token 身份）
柜机 每 1.5s 轮询               → GET .../poll，CONFIRMED 即原子消费，返回柜机侧 token
```

**关键约束**：`CONFIRMED → CONSUMED` 用 `UPDATE ... WHERE status='CONFIRMED'` + `rowcount==1` 判定，并发轮询只有一个能拿到 token，第二个只会收到 `CONSUMED` 且 `token=null`。因此二维码被截图也无法二次登录。

### 5.3 手机远程开柜：指令队列 + 回执

**问题**：手机在用户手上，柜门在墙上。手机不能直连柜机（无固定地址、无鉴权通道）。

**方案**：`t_device_command` 三态队列。

```
手机 POST /api/m/pickup/open
      → 校验归属/缴费 → business.do_unlock() 改包裹状态 → 写 PENDING 指令（含幂等键）
柜机 GET /api/device/commands/poll?cabinet_id=N
      → 取走 PENDING 置 SENT（取走即置位，避免重复执行）
柜机 POST /api/device/commands/<id>/ack
      → ACK 表示柜门已弹开 / FAILED 记录原因
```

**收益**：手机端只"下指令"，柜门是否真开以柜机回执为准——这是与"手机直接改数据库"的本质区别，也是异常排查的依据。幂等键让网络抖动重试不会二次开柜。

### 5.4 通知：入队与投递解耦

**问题**：短信通道可能超时或失败，不能让它拖慢存件接口。

**方案**：业务事务内只写 `t_notice`（status=PENDING），后台 daemon 线程每 15 秒轮询投递；失败按 30/120/600 秒退避重试，最多 3 次，超限置 FAILED 并记录 `last_error`；同一 `biz_key + channel + 接收人` 唯一，避免重复轰炸。

**收益**：存件接口耗时与短信网关无关；`NOTIFY_WORKER=0` 可关掉线程做可控测试。

### 5.5 幂等：唯一索引 + 响应快照

开柜请求带 `Idempotency-Key`。服务端先查 `t_device_command.idempotency_key`，命中且有 `response_json` 就直接返回首次结果；并发插入冲突时也回查快照。保证"同一逻辑请求无论重试多少次，只开一次柜"。

### 5.6 格口分配：事务内行锁

```
BEGIN
  SELECT cell_id ... WHERE cabinet_id=? AND size_type=? AND status='FREE'
  ORDER BY cell_id LIMIT 1 FOR UPDATE      -- 行级排他锁
  UPDATE t_cell SET status='OCCUPIED'
  INSERT INTO t_package (...)
COMMIT
```

两个快递员同时存件时，后到者被锁阻塞，拿到的是下一个格口，不会出现"两人抢同一格口"。`db.transaction()` 用 `SET AUTOCOMMIT=0/1` 显式开关事务，兼容连接池返回的 SteadyDB 包装连接。

## 6. 一次取件的完整数据流

```
① 用户扫码
   柜机 ──POST /api/qr/ticket──→ 服务端
   服务端 ──INSERT t_qr_ticket(PENDING)──→ MySQL
   柜机 ←─ticket + deep_link── 服务端
   柜机 渲染 SVG 二维码（/api/m/qr.svg?data=...）

② 手机确认
   手机 ──GET /m?ticket=xxx──→ 服务端（返回 mobile/index.html）
   手机 ──GET /api/qr/ticket/xxx──→ 服务端 → 柜机编号/位置/剩余时间
   手机 ──POST /api/qr/ticket/xxx/confirm (Bearer 用户token)──→ 服务端
   服务端 ──UPDATE t_qr_ticket SET status='CONFIRMED' WHERE status='PENDING'──→ MySQL

③ 柜机登录
   柜机 ──GET /api/qr/ticket/xxx/poll──→ 服务端（每 1.5s）
   服务端 ──UPDATE ... SET status='CONSUMED' WHERE status='CONFIRMED'──→ MySQL
   服务端 签发 USER token → 柜机存入 sessionStorage

④ 柜机取件
   柜机 ──GET /api/business/my-pickup?cabinet_id=1──→ 服务端 → 待取列表
   柜机 ──POST /api/business/unlock {package_id}──→ 服务端
   服务端 business.do_unlock()：校验状态 → UPDATE t_package(PICKED) → INSERT t_pickup_record
   服务端 notify.enqueue(PICKUP_RECEIPT)
   柜机 展示格口号 + 30 秒倒计时
```

## 7. 接口设计约定

### 7.1 风格

- REST 风格，资源名复数：`/api/packages`、`/api/cabinets`；
- 统一前缀：管理端与通用资源 `/api/*`，业务流 `/api/business/*`，手机端 `/api/m/*`，扫码 `/api/qr/*`，柜机设备 `/api/device/*`；
- 请求与响应均为 `application/json; charset=utf-8`；
- 时间统一 `YYYY-MM-DD HH:MM:SS`，服务端按 RFC 1123 序列化，前端用 UTC 组件还原避免 ±8h 偏移。

### 7.2 鉴权

**全项目统一约定（Lead 裁决，2026-11-18）：用户态凭据一律走 `Authorization: Bearer <token>`。**
早期契约文档 `docs/api-innovations.md` 曾写作 `X-Kiosk-Token`，已废弃并统一到 `Bearer`——理由是本表就是既有的运行实现，且全部回归测试依赖它。

| 端 | 凭证 | 传递方式 | 有效期 |
|---|---|---|---|
| 管理端 | `username\|ts\|sig`（HMAC-SHA256 截断 16 位） | HttpOnly Cookie `locker_admin`，兼容 `Authorization: Bearer` | 12 小时 |
| 触屏端 / 手机端 | `role\|rid\|ts\|sig`（role ∈ USER/COURIER） | `Authorization: Bearer` | 12 小时 |
| 柜机设备 | 无（演示环境） | — | — |

**两类例外（不算违反上面的统一约定）**：

| 端点 | 鉴权方式 | 原因 |
|---|---|---|
| `POST /api/pay/notify/alipay` | RSA2 签名验签，不带用户 token | 服务端到服务端回调（支付宝发起），不存在用户登录态 |
| `/api/device/*` | 无鉴权 | 已知未修欠账，见 `docs/03` §7 已知限制 #2 |

### 7.3 错误约定

| HTTP | 语义 | 响应体 |
|---|---|---|
| 400 | 参数校验失败 | `{"error": "具体原因"}` |
| 401 | 未登录 / token 无效 / 验证码错误 | `{"error": "..."}` |
| 402 | 需要先缴费 | `{"error":"NEED_PAYMENT","overtime_fee":1.0}` |
| 403 | 越权（操作他人包裹） | `{"error": "..."}` |
| 404 | 资源不存在 | `{"error": "..."}` |
| 409 | 状态冲突 / 重复确认 / 引用冲突 | `{"error": "..."}` |
| 410 | 二维码已过期/已使用 | `{"error": "..."}` |
| 429 | 验证码发送过频 | `{"error": "..."}` |
