## 1. 为什么需要这份文档

`docs/01`–`06` 是在本项目第一轮就写完的（2026-11-17，v1.0），当时的功能边界是"触屏端 + 手机端 + 管理端 + 扫码登录"。
本轮又追加了 4 组创新功能（DeepSeek 智能寄件、包装准备协同、高德找柜、支付宝沙箱支付），并引入了质量工具链证据。

于是产生了三类风险：

1. **数字漂移**：文档里的行数、表数、用例数、数据基线，写成后没再回填；
2. **接口漏记**：有接口实现了但没写进《详细设计说明书》；
3. **范围过期**：文档明确写"不做真实支付"，而本轮恰好做了支付（模拟 + 沙箱）。

本文件把这三点逐条列清，并给出"改哪里、改成什么"。**T4b 生成的实验报告与答辩 PPT，只能引用改完之后的版本**，否则答辩现场一旦被问"你说的 312 条包裹在库里查不到"，很难解释。

### 2.3 鉴权描述与实际实现冲突（**已裁决：统一 `Authorization: Bearer`**）

| # | 级别 | 位置 | 冲突内容 |
|---|---|---|---|
| G-12 | **P0** | `docs/api-innovations.md` §0.2 vs `backend/auth.py` | 契约文档原写用户/快递员凭据放在 `X-Kiosk-Token` 请求头；而 `auth.kiosk_identity()` 实际读的是 `Authorization: Bearer <token>` |

**裁决结果：已裁决（Lead，2026-11-18）— 统一 `Authorization: Bearer <token>`，废弃 `X-Kiosk-Token`。**

裁决理由（三条，按权重）：

1. **它是仓库原有的、正在运行的鉴权实现**。触屏端、手机端 H5、管理端的既有接口以及全部回归测试（`test_qr_login` / `test_route_separation` / `test_pickup_payment_gate`）都依赖它。改代码要动 5 个模块并重跑全部用例，改文档只动一处文字。
2. **改文档的风险远低于改运行代码**。鉴权是安全边界，动它的回归面最大；而契约文档尚未被最终的联调流程完全依赖。
3. **`docs/02` §7.2 与 `docs/03` §3 原本就写的是 `Bearer`**，即仓库内有 2 份文档 + 1 份代码一致，只有契约 1 份文档写成了 `X-Kiosk-Token`。按"少数服从多数 + 以代码为准"，应改的是契约。

代码证据（`backend/auth.py::kiosk_identity()`）：

```python
token = (request.headers.get("Authorization") or "").replace("Bearer ", "").strip()
```

**例外（必须一并记住的边界）**：

| 端点 | 鉴权方式 | 为什么是例外 |
|---|---|---|
| `POST /api/pay/notify/alipay` | **不带用户 token**，靠 **RSA2 签名验签** | 服务端到服务端回调（支付宝服务器发起），不存在"用户登录态"这回事；用签名证明来源 |
| `GET /api/device/commands/poll` 等柜机设备接口 | **无鉴权**（演示环境） | 见 `docs/03` §7 已知限制 #2，属**已知未修**项，不是本裁决的例外设计 |

> 一句话：**用户态一律 `Authorization: Bearer`；服务端到服务端用签名；柜机设备接口鉴权仍是已知欠账（未修）。**

后续动作：

| 责任方 | 动作 | 状态 |

| backend-engineer | 修改 `docs/api-innovations.md` §0.2 为 `Authorization: Bearer` | 进行中 |

影响：若前端按旧契约只用 `X-Kiosk-Token`，所有手机端鉴权接口会返回 401。当前 `frontend/js/api-core.js` 同时发送两个头，处于兼容状态，因此**线上功能不会因为这次裁决而中断**。

## 3. 一个必须先讲清的环境前置：`db/objects.sql` 不是可选项

这是本次盘点里**唯一一个会导致"照着文档做却跑不通"**的问题，值得单独一节。

现象：`GET /api/packages/<id>/detail` 返回 500。

```
pymysql.err.ProgrammingError: (1146, "Table 'smart_locker.v_package_detail' doesn't exist")
```

原因：`init_database.sql` 的注释写"包含所有表结构 + 全量数据"，**但视图、触发器、存储过程不在里面**，必须再执行 `db/objects.sql`。

连带影响（实测）：`db/objects.sql` 未执行时，单元测试会失败 —— 因为取件后释放格口是靠触发器 `trg_package_after_update` 完成的：

```
FAIL: test_pickup_succeeds_after_payment
AssertionError: 'OCCUPIED' != 'FREE'
```

也就是说，**"32/32 通过"这个结论有一个隐含前提：视图与触发器已建**。`docs/04` §5.3 没写这个前提，`docs/05` §3.2 写了但用的是"会出两个症状"的模糊表述。

建议在 `04` §5.1 与 `05` §3 都把前置写成硬性检查：

```bash
mysql -uroot -p smart_locker -e "
  SELECT (SELECT COUNT(*) FROM information_schema.VIEWS
           WHERE TABLE_SCHEMA='smart_locker')    AS views_,        -- 期望 2
         (SELECT COUNT(*) FROM information_schema.TRIGGERS
           WHERE TRIGGER_SCHEMA='smart_locker')  AS triggers_,     -- 期望 1
         (SELECT COUNT(*) FROM information_schema.ROUTINES
           WHERE ROUTINE_SCHEMA='smart_locker')  AS procs_;        -- 期望 3
"
```

三者不是 `2 / 1 / 3` 就先跑 `db/objects.sql`，别急着怀疑代码。

> 另一个实测到的噪声：并发开发期间多人同时在重置数据库，会看到行数在 122/120、312/310 之间跳。
> 采集基线数字时请**先确认没有别人在跑脚本**，或者干脆以 `scripts/seed_row_counts.py` 直读 `init_database.sql` 为准（本文件的 G-01～G-04 就是这么取的）。
