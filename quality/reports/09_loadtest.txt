 二、C 场景判重：无重复格口分配 —— 三重证据展开
==============================================================================
  结论行：✅ 并发存件**无重复格口分配**，也未出现同一格口被多条包裹同时占用。

  证据①（接口响应层）
    40 次成功存件（HTTP 201）各自返回了 cabinet_code + cell_code。
  证据②（内存判重层）
    分配合计 = 40；唯一格口数 = 40；重复分配 = []       → ✅ 无重复
  证据③（直查数据库层）
    本次压测产生的包裹数 = 40；同格口多条包裹 = []；包裹格口映射条数 = 40；
    全库重复占用格口 = []；格口状态不一致数 = 0        → ✅ 无重复占用、状态一致
  综合：✅ 无重复格口分配（三重证据一致）

  为什么这一条能通过：store() 把"选空闲格口"与"写包裹 + 置 OCCUPIED"放在
  **同一个数据库事务**里，且选格口用的是
      SELECT ... WHERE status='FREE' ... ORDER BY cell_id LIMIT 1 FOR UPDATE
  行级排他锁在事务提交前一直生效，因此并发请求会被串行化到"谁先锁到谁拿"。
  ✅ 业务正确性达标：任何一个格口不会被两条包裹同时占用。

  ⚠️ 但同一把锁也是 20 并发下环形等待的成因（锁的是"扫描到的整段 FREE 行"，
     而不只是最终选中的那一行）。正确性与性能在这一条 SQL 上互相拉扯，
     详见 10_store_lock_deadlock.txt。换句话说：C 场景"判重通过"和
     "20 并发卡死"是同一处实现的**两个面**，不能只引用前者。

  根因与修复（"发现 → 定性复现 → 修复 → 回归验证"闭环）
  ------------------------------------------------------------------
  根因（修复前 backend/business.py 的 _charge_overtime()）
      SELECT ... WHERE package_id IN (...)                    ← 不加锁、不开事务
      → 逐个 UPDATE t_package SET overtime_fee_paid=1 ...     ← UPDATE 不带
                                                                 "AND overtime_fee_paid=0"
                                                                 条件，也不看 rowcount
      → 逐个 INSERT t_exception_log ... 'TIMEOUT' ... 'RESOLVED'
    "读 → 判断 → 写"三步之间没有事务包裹、没有行锁、没有条件更新兜底，
    所以 N 个并发调用会同时读到 overtime_fee_paid=0、同时判定"应计费"、各写一条流水。
    金额本身被 overtime_fee 的绝对值覆盖写，不会多扣钱；但**流水与对账口径被污染**。

  定性复现（不依赖并发时序，结果稳定可重跑）
    脚本：quality/_r3c_payu_race_proof.py
    原始输出：quality/reports/_r3c_payu_race.txt
    做法：两个真实连接把上述窗口显式撑开，两组对照 ——
      A 现状写法（无锁 SELECT → 判定 → 写流水）：T1、T2 **都**判定"应计费"，
        各写 1 条 → 两边都写 = 重复入账
      B 对照写法（SELECT ... FOR UPDATE → 判定 → 写流水）：
        T1 拿到锁先写；T2 在 SELECT 上等了 5361.4 ms，读到 overtime_fee_paid=1，
        判定"跳过（已缴）"→ **只有 1 方写入**，幂等成立
    → 加锁可收敛该缺陷；这也反证了根因就是"无锁读后判断"。
    数据安全：取证用包裹取自现成演示数据（package_id=1），
              改动前先做快照、结束后精确还原；
              收尾核对"与取证前一致？ 是 ✅ 无残留"。

  实际修复（R9b，由 backend-engineer 落地，backend/business.py:937-946）
      updated = db.execute(
          "UPDATE t_package SET overtime_fee_paid=1, overtime_fee=%s "
          "WHERE package_id=%s AND status='EXPIRED' AND overtime_fee_paid=0",
          (fee, r["package_id"]))
      if updated != 1:
          continue        # 并发竞争失败：已被别的请求入账，本次幂等空转、不写流水
      # 只有 rowcount==1 才走到这里 INSERT 流水
    —— 即"条件更新（CAS）+ rowcount 兜底"，与本节原有的修复建议第 1 条一致。

    数字不可混用，但**结论方向一致**。

  ⚠️ 一个"曾被考虑但否决"的方案（设计权衡，应写进答辩）
    曾建议：在 t_exception_log 上建 (package_id, exception_type) 唯一索引，
    让重复插入在数据库层直接失败。**该方案被否决**，理由成立：
      t_exception_log 的同一件包裹在超时流转中天然会写多条 TIMEOUT 记录 ——
      转 EXPIRED 时写一条 TIMEOUT/PENDING，缴费成功再写一条 TIMEOUT/RESOLVED。
      如果建 (package_id, exception_type) 唯一索引，第二条就会插入失败，
      直接打爆正常的超时流转流程。
    → 结论：唯一索引约束的粒度不对（应该约束 "PENDING 只能一条" 或
      "RESOLVED 只能一条"，而不是整个 exception_type），
      在现有表结构下用 CAS + rowcount 是更小代价的正解。

  根因（修复前）
    backend/business.py 的 pickup()：
        pkg = SELECT * FROM t_package WHERE pickup_code=%s     ← 读
        ... 判断 status 是否为 PICKED（读到 STORED 就放行）      ← 判断
        UPDATE t_package SET status='PICKED' ...               ← 写（无 WHERE status 条件）
        INSERT INTO t_pickup_record ... 'SUCCESS'
    "读 → 判断 → 写"同样没有事务、没有行锁、没有条件更新，
    与 D 场景是**同一类缺陷**（同一业务规则存在两条无锁代码路径）。
    _do_unlock()（无码开柜路径）也是同一写法。

  实际修复（R9b，backend/business.py:741-746 与 :988 附近两处）
     updated = db.execute(
         "UPDATE t_package SET status='PICKED', pickup_time=NOW() "
         "WHERE package_id=%s AND status IN ('STORED','EXPIRED')", (pkg["package_id"],))
     if updated != 1:
         reason, code = _pickup_race_lost(pkg["package_id"], "CODE", "USER")
         return jsonify({"error": reason}), code
     # 只有 rowcount==1 才写 SUCCESS 流水
    —— 把"状态校验"与"状态变更"合成一次原子操作，无需显式加锁。
    管理员强制开柜路径（backend/business.py:1105）同样改为 CAS，
    但状态集合沿用它自己的 ('STORED','EXPIRED','EXCEPTION')。

  回归验证：三条路径都验了，不是只验一处
    · E① 取件码 /api/business/pickup        → 1×200 + 9×409 + 1 条 SUCCESS  ✅
    · E② 无码开柜 /api/business/unlock       → 1×200 + 9×非200 + 1 条 SUCCESS ✅
    · E③ 管理员 force-unlock                 → 只留 1 条 ADMIN SUCCESS       ✅
    连跑 5 轮全部通过（quality/retest_race_stability.py）。

  ⚠️ 这条修复的教训（可直接用于答辩）
    D 与 E 是**同一类缺陷的两个实例**：业务规则（"只能成功一次"）被写在
    两条不同的代码路径上，而两条路径各自"读 → 判断 → 写"，都没做原子化。
    有意思的是：同一文件第 305-307 行的揽收/撤回路径**本来就有** rowcount 兜底 ——
    说明团队知道怎么写，只是这两条更热的路径漏了。
    这正是 PPT 第 15 页"三个共同教训"里第①条的实证：
    **同一业务规则出现在两条代码路径上，就一定会分叉。**

      init_verify.sql 的 INSERT 语句里（exception_id 固定为 49 与 96）；
    · 时间戳是 2026-07，远早于本轮任何压测（压测是 2026-11-18）；
    · 压测产生的流水 remark 形如 "扫码支付超时保管费 ¥1.00"，
      全库只有 1 条（本次复测造的那条，已随清理删除）。
    · 复核 SQL：
        SELECT exception_id,package_id,occur_time,handler,remark
          FROM t_exception_log
         WHERE package_id=200 AND exception_type='TIMEOUT'
         ORDER BY exception_id;

  结论：这是**演示种子数据自身的一处不一致**（同一件包裹被种了两条超时记录），
        与本次 D 场景的并发缺陷无关，不构成本次修复的遗留。
  处置：**不清理**。理由 —— 它是种子数据的真实样貌，删掉会让
        "init_*.sql 与库内一致"这条可复核性断掉；
        若评审追问，正确答案是"这属于种子数据，不是并发缺陷"，
        而不是悄悄删掉。已在本文档留档说明。
