 ★ 结论（先看这里）
==============================================================================
  判定：**这是缺陷，且尚未修复（已知限制）**，不是"已修复"。

  一句话：store() 的选格口 SQL 在高并发下会形成 InnoDB 行锁**环形等待**，
          20 并发时 10 个事务互相卡死、40/40 请求全部 30s 超时，并拖垮整个服务。

  三个必须同时说清的点：
    ① 业务正确性没破 —— 格口不会被重复分配（详见 09_loadtest.txt 的 C 场景，
       三重证据一致）。挂的是**可用性**，不是数据一致性。
    ② 代码未改 —— 本轮 quality 只做定位与留证，不改 backend 业务代码；
       backend/business.py 的 store() 至今仍是
           SELECT ... WHERE status='FREE' AND size_type IN (...) 
             ORDER BY cell_id LIMIT 1 FOR UPDATE
    ③ 已写进交付物 —— PPT 第 15 页「问题与解决」表格第 6 条明确写
       "（未修复）"，答辩口径为"当众认账"，不假装已修。

  为什么不是"死锁"而是"环形等待"：MySQL 的死锁检测通常会在数秒内挑一个牺牲者回滚，
  但本次现场没有自动回滚，表现为**所有事务一起挂住直到客户端 30s 超时**。
  两者的处置方向一致，但现象不同，这里按实际观测写"环形等待"。

 二、根因（对应 backend/business.py store()，第 157–193 行）
==============================================================================
  SQL:
      SELECT cell_id, cabinet_id, cell_code, size_type FROM t_cell
       WHERE status='FREE' AND size_type IN (...)
       ORDER BY cell_id LIMIT 1 FOR UPDATE

  三个成因，按影响从大到小：
    1) FOR UPDATE 锁的是**扫描到的整段 FREE 行**，不是最终选中的那 1 个格口。
       InnoDB 在 RR 隔离级别下对扫描区间加锁，`ORDER BY cell_id LIMIT 1`
       并不会把锁收敛到最后返回的那一行。
    2) 缺 (status, size_type, cell_id) 组合索引 —— 实测 t_cell 现有索引是
       PRIMARY(cell_id)、uk_cabinet_cell(cabinet_id,cell_code)、
       idx_cell_cabinet(cabinet_id)、idx_cell_cabinet_status(cabinet_id,status)，
       没有一条以 status 打头、也不含 size_type，
       所以优化器只能沿 PRIMARY 顺序扫，扫描集合随 FREE 行数变大而变大。
       本机 t_cell 共 720 行、FREE 589 行 —— 锁面几乎覆盖半张表。
    3) 并发越高，事务互相等待的链越长，最终成环。

  实测佐证（当前库状态，只读查询）：
      EXPLAIN ... WHERE status='FREE' AND size_type IN ('SMALL')
              ORDER BY cell_id LIMIT 1 FOR UPDATE
      → type=index, key=PRIMARY, rows=1, Extra="Using where"
      即沿主键全序扫描再过滤，没有用到任何状态索引。

 三、影响面（说清楚"什么时候会踩"）
==============================================================================
  · 20 并发存件：10 个事务成环、40/40 请求超时、服务整体不可用 —— 已实测复现
  · ≤10 并发存件：三轮各 40 次全部成功、格口无重复（09_loadtest.txt C 场景）——
    说明缺陷有明确触发阈值，不是"一直坏"
  · 压测脚本据此把 C 场景收敛到 ≤10 并发，并把 20 并发档单独作为缺陷复现记录，
    不混进吞吐统计当正常数据 —— 这是"不让缺陷污染性能结论"的处理方式

 四、复现与修复建议
==============================================================================
  复现（只读观测，随时可重跑）：
      python quality/diagnose_store_locks.py      # 打印当时的锁现场与等待图
      python quality/repro_store_deadlock.py      # 两连接对照复现锁冲突
  注：repro_store_deadlock.py 在**空闲库**上可能复现不出（两次都成功拿到锁），
      这属于正常 —— 该争用依赖真实并发时序，以压测原始数据为准。
      R3c 复跑记录见 quality/reports/_r3c_lock_snapshot_now.txt（当时已无等待）。

  修复建议（供 backend-engineer 参考，本轮 quality 不改业务代码）：
    1) 单行原子占用，最直接：
         UPDATE t_cell SET status='OCCUPIED'
          WHERE cell_id = (SELECT ... FROM (SELECT cell_id FROM t_cell
                              WHERE status='FREE' AND size_type IN (...)
                              ORDER BY cell_id LIMIT 1) t)
            AND status='FREE'
       再判 rowcount == 1；==0 就重试。这样锁面收敛到真正被更新的那一行。
    2) 或使用 `FOR UPDATE SKIP LOCKED`（MySQL 8.0 支持，本机 8.0.39）：
       多个事务各自跳过已被别人锁住的行，天然不成环。
    3) 或补索引把锁面收窄：
         ALTER TABLE t_cell ADD INDEX idx_cell_free (status, size_type, cell_id);
    4) 事务内不要放旁路操作：目前 notify.safe_enqueue() 已在事务外，这点是对的，
       应保持 —— 事务里持有行锁的时间越短越好。

 五、为什么这一条和 09 的 C 场景"结论相反"
==============================================================================
  C 场景判重结论是 ✅（无重复格口分配），本文件结论是 ❌（20 并发卡死）。
  **两者不矛盾，是同一处实现的正确性与性能两个面**：
     FOR UPDATE 这把锁正是"不重复分配"的保证（正确性 ✅），
     也正是在高并发下成环的原因（性能/可用性 ❌）。
  答辩时如果只引用 C 的 ✅ 而不提本条，等于把"用牺牲并发换来的正确性"
  说成了"没有代价"。正确口径是两句一起说：
     "格口不会被重复分配，代价是 20 并发下会因为行锁成环而卡死，这一条未修复。"
